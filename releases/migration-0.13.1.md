# Program Kit 0.13.1

This release makes a typed Foundation composition the single application startup
definition and repairs planning, preserved-proof pickup, verification isolation,
identity projections, affected-project inventory and complete lock renewal.
New projects receive the qualified Foundation 0.3.3 profile and its exact
publisher knowledge, including authenticated HostedPages routes. Existing consumers
retain their accepted profiles, custom configuration, owners and native locks.

## Application composition migration

For an Accepted application/runtime selection, populate schema version 2 of
`eng/foundation-composition.json` before normal engineering synchronization. Link
its resources to the Accepted owner/placement decisions: hosts, API features,
separate database servers and logical databases, identity authority, clients,
audiences and frontends. Generated settings, Keycloak imports and Docker Compose
are outputs. `Dev.ps1` is retired; no aggregate `.Composition` project is needed.
Library-only selections continue to use ordinary engineering checks.

Use `composition_migrate.py` from the verified release's .NET scripts directory to
preview an existing v1 input, or supply `--proposal <local-reviewed-v2.json>` when
the consumer has no composition input. Pass `--repository <consumer>` and apply
the exact returned digest with `--apply --plan-digest <digest>`. The importer
archives the original and rejects changed Accepted inputs, plans, tasks or locks.
It preserves product code and delivery state. Review affected Accepted placements
and reconcile their existing materialization before resuming the supported updater;
an engineering preview that reports PKM003 needs this population first.

After installation, reconcile the managed scaffold and resolve actual source
conflicts. Run `python eng/composition_run.py prepare`, then `run`. Preparation
owns acquisition, frontend builds, database provisioning and owned identity
registration reconciliation. Normal startup checks actual authentication, theme,
assets and selected provider activation. `update` selects changed compilation
dependants; `update --host <id>` includes affected dependants; `stop` retains data.
The implementation prehook uses the same prepared startup path.

Keep future product interfaces and provider bindings in the Accepted architecture
plan. Foundation preparation checks planned boundaries and performs real compilation,
packaging and selected runtime admission; it does not require those future product
bindings to be implemented first. Full compiled-product architecture verification
remains required during affected implementation and acceptance.

Reconcile affected plans/tasks in place and enter implementation in a fresh
invocation of the same feature. Keep valid code, task IDs, requirements, Accepted
history, original native locks, baseline and accumulated effort. Do not restart
intake/bootstrap or import stale completion checkmarks. Product authorization,
ownership, transactions, idempotency and human journey review remain due.

Initial executable coverage is managed Keycloak, PostgreSQL and BFF application
hosts with multiple resource instances. External resources and neutral call intents
have distinct model bindings; unsupported adapters/handshakes fail before execution.
The published path does not promise production identity provisioning or unqualified
providers. Current Windows evidence uses fresh consumers on a prepared host, not a
fresh Windows OS installation.

## Upgrade and optional Foundation adoption

Install through the supported resumable consumer updater. Preserve original inputs,
local repairs, failed attempts, historical proofs and accepted architecture. Normal
sync reconciles the identity version/digest from one immutable authority and supplies
shared verification mappings. Required provider-test isolation remains consumer-owned;
missing or invalid isolation stops dispatch rather than exposing credentials.

An already fresh 0.13.0 story needs no new reset, constitution ratification or clock
baseline. Keep stable task IDs, completed work, human decisions and cumulative effort.
Repair a failed implementation preflight, close that invocation, then require a fresh
successful invocation before affected source work. Hooks remain once per invocation.

Foundation 0.3.3 adoption is optional and requires the existing exact dependency
transition review. Typed HostedPages Routes own distinct IDs/paths/revisions and
Public/Authenticated page access. Bootstrap inherits page admission and may add
restrictions; route-specific URLs prevent shared content revisions from bypassing
permissions. BFF session admission, canonical permissions and the final WebDefaults
header writer remain the existing mechanisms. Public immutable code assets are
admitted separately; application APIs own protected data and resource/state checks.
Retained 0.3.2 HostedPages remains public-only.

## Preparation and evidence

Settle selection, placement, configuration, executable fixtures and native locks
before prerequisite proofs. Preview receipt invalidation; unproved independence
retains conservative whole-selection binding. Preview stale fixture pickup with the
installed `fixture_readiness.py --repository . --contract <contract> --identity <new-id>`.
Apply only its reviewed exact plan digest. Original inputs are archived; the new
fixture is a draft, not compatibility proof or paid authorization.

Renew the complete affected reverse-dependent project closure in one reviewed batch,
then run whole-solution LockedMode. Literal semicolon-separated MSBuild items have
the same inventory as split items. Dynamic/unmapped inputs require a proved evaluated
adapter; zero tests and an unrequested full-suite fallback are not success.

Check actual shared executable paths/versions, Docker Linux/access, immutable image
digests and required browsers before behavior. BFF's early Chromium prerequisite
does not claim the full browser journey complete. Device installations remain
user-terminal work. Preserve reservations, unknown paid outcomes and one-use phase
authority; installation/pickup does not retry or reset them.

## Verification and recovery

Verify installation coherence, retained profiles/locks, current applicable Foundation
knowledge, affected scoped checks and actual fixture behavior. Private-page adoption
must exercise anonymous/denied/admitted entry, conjunctive bootstrap permissions,
shared-revision isolation, public assets, final headers, logout/re-entry and discovery
exclusion. Human story acceptance remains separate.

Repair a reported failure and resume the same supported updater with preserved
original evidence. A corrected local candidate may use only its explicitly reviewed
original release fingerprint; ordinary updates receive no repair exception. Toolkit
or Git recovery cannot undo live data/identity changes. Local Release uses Chromium
and WebKit; CI retains Firefox. Publication requires the complete tagged workflow.
