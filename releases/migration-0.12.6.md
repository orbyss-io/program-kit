# Program Kit 0.12.6 candidate

This candidate is unpublished. Foundation exporter 0.2.4 must pass its protected
publication and availability gates before Program Kit can advertise that default.

Program Kit upgrades capture and preserve the accepted dependency profile, exact
catalog bytes, native lock and architecture choices. An exporter change requires
the explicit producer reconciliation option; a general dependency change uses
the separate Draft, review and Accepted transition. Existing accepted choices
remain the authority. New profiles require qualification before support.

General transitions preserve a sealed Accepted review and recover interrupted map,
selection and profile writes. Bind both the profile and transition review hashes.
New scoped compatibility receipts bind the artifacts exercised by their fixtures;
an unrelated dependency change can retain them. Historical receipts retain their
original strict bindings and require lifecycle renewal before adopting that scope.
Verified historical scratch fixtures remain identifiable during installation even
when tooling changes. Their original receipts, inputs and execution outputs must
still match; active application references remain rejected. This classification
does not establish current compatibility or migration completion.

Review stale compatibility proofs through the maintained post-bootstrap lifecycle.
Keep historical approvals and receipts. Read the changed tooling list in the
qualification report; do not rewrite old proof hashes. Exporter reconciliation
invalidates affected analysis and reports its renewal commands. Repository-local
tool discovery accepts exact staged SDK, Node archive and npm archive layouts;
it checks versions and does not change machine-wide installations.

New publisher packages use canonical `orbyss-foundation/feature.json`. Consumers
retain the identical descriptor alias bridge until the Foundation-owned build
package is publicly available. New publisher metadata declares feature identities,
dependencies and routes, including private runtime dependency facts. Historical
descriptor-less Foundation 0.2.2/0.2.3 inputs use a bounded immutable bridge.

Run the updater with `--plan` first. For this migration, bind the exact plan digest
in an Accepted architecture decision and register the migration review before
installation. Sources older than 0.12.5 additionally need a reviewed bridge.
After synchronization, run supported native lock verification and the consumer's
activation/export/browser pipeline. Installation coherence alone is not consumer
readiness. An incomplete migration or pending proof must retain its diagnostic.
The updater records `migration-completion.json` and returns a pending result when
required dependency or phase verification is missing. Repeating `--plan` retains
the original unfinished migration rather than treating installed files as success.

Retry the same verified release after a failure. Original inputs are sealed in
the upgrade attempt; missing, changed or contradictory evidence stops recovery.
Preserve the failed attempt rather than inventing installed-version provenance.

PR validation now selects from declared affected inputs and runs up to four workers
on Linux with prerequisite and resource locks. Main runs Development and Windows
integration; tagged Release still requires complete exact-commit evidence.
Firefox remains in CI. Historical retirement checks move to weekly maintenance.
Program Kit retains consumer installation, upgrade and browser boundaries; Forms
owns its component admission cases. CI timing improvement still needs measurement.

Release notes, this cumulative migration guidance and its machine index ship as
checksum-bound GitHub assets and inside verified offline bundles. Durable
contributor publication and failed-tag recovery instructions remain in
`docs/releasing.md`.
