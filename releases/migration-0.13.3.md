# Program Kit 0.13.3

This guide applies to 0.13.3. Availability is established by successful exact-source CI qualification, promotion and public installation/upgrade verification.

## Maintenance repairs and safe adoption

This release carries the approved frozen 47-finding maintenance batch. The maintained updater retains authentic original component source and attempt inputs, resumes verified interrupted mutation boundaries, preserves authored/custom files and rejects unexplained mixed state. Native installed phase/command loading, restore and pack closure, exact regression execution, document/task/material ownership, settings and typed client integration, prepared frontend freshness, bounded provider/file operations and disposable database lifecycle receive central repairs. The implementation ledger records their individual evidence and limits.

Upgrade through the supported installer/updater. Keep existing accepted profiles and locks unless explicitly adopting the new qualified public Foundation runtime 0.3.6, Build 0.3.2 and exporter 0.2.7 closure. New defaults and versioned publisher knowledge are qualified together; historical profiles remain immutable.

Retain current application code, custom frontend/editor logic, accepted decisions, task IDs, effort, failures, data and uncertain provider outcomes. This maintenance upgrade supersedes the earlier blanket unfinished-feature delete/restart direction. It does not itself authorize consumer deletion, a bootstrap restart, paid execution or a new human acceptance decision. Separately requested consumer restart work remains separate.

Customized managed seams receive precise reconciliation conflicts. Presentation adoption binds the actual native package contracts and reviewed entrypoint bytes; cancellation preserves local work, and expired sessions remove private presentation without replaying an operation. Check the actual supported composition/profile disposition before execution.

After installation, verify coherence and affected native restore/build/pack/frontend and behavior checks. Use the original retained recovery context on failure. Toolkit regression, historical consistency and application acceptance remain distinct.

## Repair-feedback additions

This indexed guide describes feature-branch source intended for a future release;
it does not announce public availability before the complete release succeeds. Public evidence infrastructure was provisioned and tested
on 16 October 2026; see the [operational results](../docs/reviews/repair-feedback-operational-test-results-2026-10-16.json).

The consumer repair reporter adds comparable diagnostic questions, explicit
unknown/retrospective explanations, selected-version provenance, bounded evidence
and independent contributor assessments. It helps Program Kit learn from local
blockades without treating a workaround or incoming hypothesis as an accepted
shared repair. [Approved specification](../docs/reviews/repair-feedback-feature-specification-2026-10-16.md)
and [owner execution ledger](../docs/reviews/repair-feedback-execution-ledger-2026-10-16.json)
record the why, changed source, actual verification and remaining dependencies.
The repair-feedback implementation was merged in [PR #42](https://github.com/orbyss-io/program-kit/pull/42). Individual consumer reports still require their own real evidence and review.

After a qualified release containing this feature, refresh native integrations
through the existing supported updater. The generated consumer skill is
`speckit-program-kit-governance-repair-request`, registered by the governance
extension command `speckit.program-kit-governance.repair-request`. The evaluator
stays repository-only. There is no new ordinary implementation hook or acceptance
authority. Existing profile/knowledge selections, consumer explanations, exact
locks and historical evidence stay intact.

First use asks whether the person contributes to Program Kit; default is consumer.
Contributor routing requires their chosen validated checkout and explicitly
registered receiving owner/ledger. See the [maintenance intake procedure](../docs/maintenance/repair-feedback.md).
Earlier contributor preferences require owner reconfiguration; original deliveries
can be explicitly bound without rewriting them. Setup discloses
ignored personal preferences and a reference/receipt index, proves ignore behavior
and keeps them outside governance digests. Preserve these files through upgrades;
they contain no credentials or current-status cache. Choices can be changed or
cleared. No existing consumer must adopt public delivery to upgrade.

Local delivery queues immutable request/revision evidence and links the owner's
existing ledger. It creates no public objects. Public delivery first searches and
inspects upstream open/closed issues, then requires review of the exact content,
issue/comment destination, consumer fork and evidence PR workflow before publication.
It fails closed if duplicate checks, prerequisites or trusted evidence-repository
configuration are unavailable. The separate evidence repository is
`orbyss-io/program-kit-evidence`; each delivery still verifies pinned workflow
enforcement and maintainer review requirements. A fork push already
publishes content; public history cannot promise erasure.

Status/history retrieves known GitHub objects freshly every time and reports failed
reads unavailable/partial. Local status freshly reads the authoritative owner ledger.
Evidence acceptance, assessment, confirmed repair, implementation, validation,
released availability and consumer confirmation remain distinct. Follow-ups retain
request identity and explicitly supersede earlier evidence hashes.
Owner intake now supports bounded discovery, complete pinned public packet import,
assessment 1.1 with owner routing, and existing finding IDs. Decisions remain in
the existing owner ledger and status matches exact request revisions and assessment
hashes. Historical assessment 1.0 and older consumer accounts remain preserved.
Later correlation appends separately instead of modifying an immutable delivery.

Validate installed source/skill generation and personal-file preservation, then the
recording-fake repair-feedback checks and bounded Development suite. CI owns full
exact-candidate qualification, including Firefox. For preparation/delivery failures,
retain the local packet and mutation journal, inspect actual remote outcomes and
retry the same reviewed identity. Never silently fall back to public delivery.
