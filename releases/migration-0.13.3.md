# Program Kit 0.13.3 — unreleased repair-feedback feature guidance

This indexed guide describes feature-branch source intended for a future release;
it does not announce availability, select a qualified candidate or change the
current package version. Public evidence infrastructure is not established.

The consumer repair reporter adds comparable diagnostic questions, explicit
unknown/retrospective explanations, selected-version provenance, bounded evidence
and independent contributor assessments. It helps Program Kit learn from local
blockades without treating a workaround or incoming hypothesis as an accepted
shared repair. [Approved specification](../docs/reviews/repair-feedback-feature-specification-2026-10-16.md)
and [owner execution ledger](../docs/reviews/repair-feedback-execution-ledger-2026-10-16.json)
record the why, changed source, actual verification and remaining dependencies.
No issue, implementation PR or accepted public evidence link exists for this
feature yet; add useful real links here when they exist rather than inventing them.

After a qualified release containing this feature, refresh native integrations
through the existing supported updater. The generated consumer skill is
`speckit-program-kit-governance-repair-request`, registered by the governance
extension command `speckit.program-kit-governance.repair-request`. The evaluator
stays repository-only. There is no new ordinary implementation hook or acceptance
authority. Existing profile/knowledge selections, consumer explanations, exact
locks and historical evidence stay intact.

First use asks whether the person contributes to Program Kit; default is consumer.
Contributor routing requires their chosen validated checkout. Setup discloses
ignored personal preferences and a reference/receipt index, proves ignore behavior
and keeps them outside governance digests. Preserve these files through upgrades;
they contain no credentials or current-status cache. Choices can be changed or
cleared. No existing consumer must adopt public delivery to upgrade.

Local delivery queues immutable request/revision evidence and links the owner's
existing ledger. It creates no public objects. Public delivery first searches and
inspects upstream open/closed issues, then requires review of the exact content,
issue/comment destination, consumer fork and evidence PR workflow before publication.
It fails closed if duplicate checks, prerequisites or trusted evidence-repository
configuration are unavailable. The separate evidence repository is intended as
`orbyss-io/program-kit-evidence`; provisioning, pinned workflow enforcement and
maintainer review must be verified before claiming it works. A fork push already
publishes content; public history cannot promise erasure.

Status/history retrieves known GitHub objects freshly every time and reports failed
reads unavailable/partial. Local status freshly reads the authoritative owner ledger.
Evidence acceptance, assessment, confirmed repair, implementation, validation,
released availability and consumer confirmation remain distinct. Follow-ups retain
request identity and explicitly supersede earlier evidence hashes.

Validate installed source/skill generation and personal-file preservation, then the
recording-fake repair-feedback checks and bounded Development suite. CI owns full
exact-candidate qualification, including Firefox. For preparation/delivery failures,
retain the local packet and mutation journal, inspect actual remote outcomes and
retry the same reviewed identity. Never silently fall back to public delivery.
