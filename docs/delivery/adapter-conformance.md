# Phase 0 delivery adapter conformance contract

This is an experimental contributor contract, not an installed delivery extension. Phase 1 owns packaging and activation. The [accepted decisions](../backlog-delivery-phase-0-decisions.md) govern this contract; the [capability evidence](phase-0-evidence.md) separates tested behavior, injected failures and limitations.

## Versioned records and authority

[contracts.schema.json](contracts.schema.json) is JSON Schema 2020-12, generated by `scripts/delivery_phase0/schema.py`. [examples.json](examples.json), generated by `scripts/delivery_phase0/examples.py`, contains synthetic examples of every record variant and both provider profiles. Closed objects reject unknown fields and unsupported schema versions. Semantic checks complement structural validation; passing JSON Schema alone does not establish readiness or authorization.

| Record | Authority and intended interpretation |
|---|---|
| Disabled profile | Core local planning only. No provider, credentials or coordination store required. This is not a local delivery backend. |
| Enabled profile | Consumer Git configuration identifies delivery space, provider/edition, native mappings, roles, coordinator and capabilities. A repository binding pins a compatible profile revision. |
| Work | Platform identity and stable logical ID, business outcome/acceptance, priority, parent, repositories, milestone and delivery state. Linked technical artifacts remain authoritative in Git. |
| Observation | Availability, native revision, business fingerprint, observation time and independent field/comment/relation/history coverage. An accepted basis is separate from the latest observation. |
| Proposal | Immutable input and payload fingerprints, operation IDs, technical basis, and an attributable role-specific approval. Any material input/payload change invalidates the approval. |
| Operation | Immutable logical operation ID/destination/payload basis, actor, expected native revision where available, dispatch/recovery state and verified native identity. |
| Claim | Accountable human, native actor, session execution ID, monotonic generation, accepted basis, last checkpoint and explicitly exclusive resources. Stale time alone cannot transfer a claim. |
| Dependency | Predecessor/successor, specific blocked activity, receiving owner, satisfaction condition, required evidence IDs and optional external reference. |
| Evidence | Producer, source and contract revisions, acceptance IDs, artifact location/hash and result. Upstream closure is not receiving integration evidence. |
| Footprint | Repo/base/head/plan identity, planned versus observed scope, coverage, paths/globs, resources, generated sources, protected assumptions and visible categories. |

The profile schema is an initial vocabulary, not an enterprise process migration engine. Native custom fields have explicit mappings, authority, readiness requirements and write policy. Credential values do not belong in any record. User-visible tags/labels are a projection of concise categories; they do not encode claims or entire file inventories. Capability values default to unverified in examples and must be backed by adapter/version/platform evidence before use.

Use immutable provider IDs for repositories, projects, users and work items; names/URLs are display and discovery data. Bindings from a different space/profile revision fail before writes. A profile upgrade is an explicit new configuration decision. Do not silently regenerate existing logical identities on import or retry.

## Conditional coordination boundary

One delivery space uses one operational branch with a complete admission snapshot. Claims that must be mutually exclusive cannot be divided into separately updated records without a new proven admission protocol. The Phase 0 reference stores JSON in `state.json`; this is operational metadata, not a second backlog.

1. Read the branch head and its state by that exact commit ID.
2. Validate the pinned profile, accepted input basis, current assignment, actor/role authority, work readiness and compatibility with active work.
3. Compute claim generation, scope and operation intent from that snapshot.
4. Publish with the expected previous branch head. Only a confirmed successful conditional commit grants entitlement.
5. On a conflict, reread and recompute the whole decision. Never submit an old decision with a substituted expected head. On ambiguous response, inspect the operation identity before proceeding.

Azure uses the push API's `refUpdates.oldObjectId`; GitHub uses GraphQL `createCommitOnBranch.expectedHeadOid`. A successful commit does not make later work-item changes transactional. Branch protection/permissions must permit authorized updates but prevent deletion/force-reset by ordinary automation. Initial setup pins the repository/branch identity and records attribution. The prototype validates its exact disposable resource IDs and markers before operating; consumer setup and durable protection policies belong to later phases.

The guarantee covers participating Program Kit sessions. It does not physically stop humans or other tools from editing files. A takeover requires the current owner or configured coordinator's authority and increments the generation. Old sessions fail their next checkpoint; they do not regain authority when a later claim is released. Never infer authority from elapsed time, a board column, native assignment alone, or permission to write the repository.

The pure reference functions accept an already-verified authorization decision from their caller; they are not an identity/role authorization service. Live probe account attribution also exists in native provider commit/work-item history. Consumer identity resolution and CI workload identity setup are implementation requirements, not supplied by the prototype.

## External mutation and recovery boundary

Creation endpoints do not expose a caller-controlled idempotency key. Before creating, commit a unique operation identity and payload fingerprint, then conditionally record `dispatched`. Embed its correlation marker in the initial work-item body. A create may be sent only after that dispatch commit is confirmed.

| Current state / observation | Allowed next behavior |
|---|---|
| Prepared with current approval and input basis | One cooperating worker commits dispatch, then sends the request once. |
| Confirmed successful creation | Record the returned provider identity as applied. |
| Dispatched; timeout, process interruption or missing completion record | Reconcile. Do not infer non-creation. |
| Exactly one verified matching item, complete relevant observation | Adopt its native identity and mark applied. Verify destination, marker and original relevant payload. |
| No matching item, delayed listing, incomplete coverage or inaccessible provider | Remain `outcome_unknown`; safely re-observe. No automatic second create. |
| Multiple matches or changed matching payload | Conflict requiring review. Preserve the items and human edits. |
| Definitively established non-creation | Record evidence as not applied; a separately identified approved attempt may follow. |

An operation journal cannot eliminate the crash interval between recording dispatch and sending a request. Unknown therefore intentionally includes requests that may never have been sent. A manual recovery decision that accepts duplication risk is exceptional, attributable and outside automatic retry. Never treat a worker timeout or takeover as proof the previous external request failed.

For updates, Azure JSON Patch `test /rev` protects the same work item being changed. GitHub shared descriptions have no proven equivalent CAS; the reference refuses replacement and posts a reviewable proposal comment. Do not confuse a comment proposal with an applied business revision. Label, relationship, comment and project-field mutations have their own partial-write/recovery obligations; proving creation recovery does not prove all of them idempotent.

Mechanical operations should be as narrow as possible. An approved parent/children proposal is a recoverable sequence, not an all-or-nothing transaction. Persist completed operations, stop only affected dependent work, and retain outstanding obligations. Automatic deletion of business work is not the default; the live deletion probe uses a specifically created synthetic item only.

## Observation, overlap and delivery verdicts

Never mark an inaccessible, incompletely observed or materially changed item ready. Track coverage for descriptions/fields, comments, relations and history separately; a single page or current body is not proof of complete history. A 404 without deletion provenance means unknown: access loss can look the same. Rate limits and outages defer new shared claims and governed completion. Bounded continuation of already-claimed work remains subject to the accepted outage policy and later checkpoint implementation.

Provider reads may lag acknowledged writes. Pin content reads to a known commit where possible; tolerate stale reads through conflict/recovery, not by weakening conditional updates. Claims, approvals and completion must never become more permissive because history or a page is missing. Session observations cannot promise detection of every transient edit without sufficient provider history; missing history requires a reconciliation baseline/review before readiness can be re-established.

Readiness and compatibility are distinct. Same category with disjoint changes can remain eligible. Overlapping writes are advisory unless a specifically incompatible resource/contract or explicit exclusive activity establishes a hard coordination requirement. Changed contracts in different repositories still conflict. Generated output paths refer back to their sources. Unknown scope, different bases and unresolved glob intersections produce uncertainty, not independence. Actual scope expansion requires reassessment; this is not a rigid file allowlist or a prediction of every merge conflict.

Evidence satisfies only the identified receiving requirement at the expected source/contract revision. Keep implementation completion, verified delivery and business acceptance distinct. Native status changes, child closure, external issue closure and agent assertions cannot substitute for those gates.

## Conformance and execution

`tests/validate_delivery_phase0.py` is offline and joins Development/CI. It imports no credential acquisition and starts no coding agent. It covers schema drift, disabled mode, version/profile mismatch, stale approvals and claims, resource contention, ambiguous creation, provider observation failures, artifact-bound evidence and overlap examples.

Live API probes are separate, explicitly invoked contributor scripts. `setup.py` is intentionally scoped to the exact approved disposable Azure/GitHub resources. Its local setup journal records resource creation before dispatch and stops on an uncertain result. It is a setup aid, not the cross-machine coordinator. `probe.py` creates run-specific synthetic items; rerunning starts a new test run, not a retry of unfinished production work. Preserve failed-run evidence and reconcile pending operations before claiming completion. It launches two ordinary Python processes for races, never coding agents.

The live harness demonstrates primitives and bounded reference behavior. It is not the full activation, reconciliation engine, branch-protection provisioner, human authorization layer or production adapter. Later phases must retain these tested boundaries while implementing those journeys.
