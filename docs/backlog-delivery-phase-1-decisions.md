## Repository findings

Phase 1 merged committed `origin/main` at `33b69e5` (0.11.0), including mandatory specification intake. The original checkout's unrelated uncommitted work was not imported. No version bump or publication is part of this phase.

- Extension distribution and upgrade logic explicitly enumerate the current extensions. Creating a directory alone will not install delivery tooling. Phase 0 scripts/schemas are contributor artifacts, not shipped runtime inputs.
- Core roadmap `Ready` currently means ready to write a specification. The task template writes Active/Delivered locally, and generated roadmap projections explicitly claim local status authority.
- Direct implementation preflight invokes lifecycle/artifact-ownership checks without directly invoking governance-state validation. Optional extension hooks alone cannot enforce enabled delivery authority consistently.
- Machine-local governance configuration can currently override paths. Delivery-space authority, provider selection and accepted profile revision must not be redirected through that mechanism.

## Accepted decisions: round 1

1. **Installation:** include an inert `program-kit-delivery` extension in the normal kit distribution/upgrade, disabled by default. Installation must require no provider identity, connection, repository creation or cloud writes. Later activation should not require consumers to rediscover and install a separate package. Disabled core checks must also tolerate a missing delivery extension in older consumers.
2. **Technical-to-business identity:** give each local roadmap/specification entry one primary canonical Requirement identity. A Requirement can link technical artifacts in more than one repository. Native Features remain capability groupings and local implementation checklists do not automatically become cloud Tasks. Create separate Requirements or Tasks only for useful independently owned outcomes/contributions. Do not introduce many-to-many primary ownership that leaves it unclear which requirement authorizes an implementation. Preserve existing local IDs and add explicit provider/logical bindings during later activation.
3. **Readiness vocabulary:** distinguish refinement/specification readiness, implementation readiness and verified delivery. Native workflow status is mapped progress, not proof of any of these verdicts. Refinement can start with sufficiently clear outcome/scope and resolved architecture-significant prerequisites; it must not require the specification/plan it exists to create. Implementation additionally needs current accepted technical basis, observable acceptance criteria, an owner, dependency/coordination assessment and a verification plan. Delivery needs matching evidence; business acceptance remains a separate attributable decision. Estimates, dates and non-applicable fields remain optional. Keep existing disabled-mode semantics intact.
4. **Shared policy and repository variation:** the shared versioned profile owns provider, hierarchy/field/state semantics, approval-role policy and coordination rules. A checked-in repository binding supplies repository/team identity, technical artifact paths and permitted team/area defaults at an explicit profile revision. Machine-local settings may hold credential-facility references/cache preferences, but cannot switch provider, disable authority, select a different policy revision or relax gates. Missing/malformed connected configuration must be diagnosed against activation provenance, not silently treated as a fresh disabled installation. Exact file layout and provenance detection follow this policy decision.

## Consequences already settled by prior phases

Phase 1 supplies contracts, templates, binding validation and the core authority seam. Actual Azure activation is Phase 2; full claims/reconciliation and GitHub parity follow later. Phase 1 must explicitly reject unsupported production delivery admission rather than treating test fixtures as provider evidence. Local drafting, inspection and technical-only validation remain available with clearly scoped results. Existing enabled-mode outage rules apply only when an actual previous valid claim/baseline exists.

All entry points that can authorize new implementation or governed completion must use the shared authority resolver. An optional hook cannot be the sole gate. The implementation must update command guidance, deterministic readers/writers, generated projections and task instructions together while preserving mandatory technical governance.

## Accepted decisions: round 2

5. **Prepared configuration versus activation:** preparing or validating configuration must not switch delivery authority. Use consumer-owned, checked-in `.program-kit/delivery/binding.json` and a separate `.program-kit/delivery/history.json`, outside installed extension directories and caches. Successful provider activation in Phase 2 will record the selected binding/profile identities, verification result and attributable decision. Preserve a linked history of activation, profile changes and explicit disconnect; normal upgrades preserve both records. Phase 1 can validate prepared records and deterministic fixtures, but cannot issue a successful production activation receipt or delivery admission before its provider capability exists. Missing/malformed records or a changed binding digest after activation are inconsistent, not implicitly disabled. No prior activation means the accepted disabled default. Compare with the established Git baseline when available to detect ordinary deletion of both working files. These records do not claim protection against wholesale removal of provenance or rewritten history.
6. **Parallel contributions to one Requirement:** retain one accountable owner and one acceptance outcome for the Requirement. When different people/sessions implement independently, create explicit meaningful child Tasks (for example API contribution, client contribution and receiving integration verification). Each execution claims its selected Task and is bound to the parent Requirement's current accepted basis. For simple work, claim the Requirement directly. An approved decomposition selects direct execution or delegated child contributions; it must not allow competing parent-wide and child implementation claims. The parent owner remains accountable without holding an exclusive parent implementation lock over all children. This phase establishes identity/decomposition fields and validation; Phase 4 implements the claim protocol and cross-repository admission tests.

## Schema promotion and phase acceptance

Promote the useful Phase 0 vocabulary into the installed extension, with explicit product schema versions, closed shapes, native-field mappings, templates and semantic validators. Preserve the historical Phase 0 schemas/probes/evidence rather than rewriting their receipts to imply they tested later product code.

One schema correction is necessary: a profile payload cannot contain the Git hash of the commit containing itself. Store semantic/schema identity and policy in the profile; keep source repository, immutable commit, path and exact-byte digest in its external binding/resolved observation. For colocated profiles, commit the profile before committing the binding that pins it. Detect tampering or mismatches using the resolved artifact identity, without inventing self-referential hashes.

Acceptance will cover disabled installation and older missing-extension consumers; preserved binding/history through upgrades; malformed/deleted/changed connected records; mismatched profile revisions/digests; minimal draft epics; separate refinement and implementation requirements; useful optional Task decomposition; current approvals; consistent authority across direct core entry points and projections; and explicit unavailable-provider diagnostics. Structural validation does not claim to judge prose quality: guided refinement and the existing attributable approval flow handle material ambiguity. Run targeted checks plus the bounded Development suite, then commit/push the phase before the next interview.
