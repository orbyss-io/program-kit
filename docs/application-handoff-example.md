# Example application handoff

Illustrative output for a fictional Orders application with an Orders API, a Reporting API and a
web client. PostgreSQL and Keycloak are dependencies required by this example's selected behavior.
The paths below describe a proposed handoff; they are not artifacts already generated by Program
Kit. Exact identities, versions, configuration keys and hashes must come from the real application.

## What the receiver gets

```text
artifacts/handoff/
  index.json                      identities and references to actual release outputs
  application/                    bundles/packages/assets or immutable artifact locations
  contracts/
    settings.schema.json          supported application settings and constraints
    orders.openapi.json           delivered Orders API interface
    reporting.openapi.json        delivered Reporting API interface
  documentation/
    application.md                purpose, capabilities, terminology and roles
    build-and-run.md              verified ordinary application commands
    review-scenarios.md            user journeys and expected outcomes
    runtime-requirements.md        requirements of the delivered application
```

Feature descriptors remain within their packages. The index links them to the existing bundle
descriptors and artifacts instead of copying their definitions into a second registry. Applicable
Dockerfiles, local Compose inputs, migrations and safe configuration examples can be referenced or
included from their existing application source locations.

## Application facts supplied to infrastructure

| Fact | Example application output |
| --- | --- |
| Identity | Orders application release, its source revision and component identities |
| Executables | Exact bundles for Orders and Reporting, static web assets and the required host image digest |
| Feature selection | Existing packaged feature descriptors and the application's shell activation configuration |
| Configuration | Accepted database/identity settings, supported binding mechanism, scope and secret classification |
| Dependencies | PostgreSQL capabilities needed by the application and accepted identity-protocol requirements |
| Runtime | Actual listening interfaces, required files, writable state and implemented health/shutdown behavior |
| Data changes | Application migration artifact, invocation and compatibility with application versions |

An infrastructure team takes these outputs into its own deployment process. Program Kit supplies
the application facts regardless of whether that process uses Azure, Bicep or another technology.

## Application facts supplied to documentation

The authored application overview explains what an order means, which users can create or view
one, how totals are calculated at the product level, and what reporting promises about consistency.
The API contracts provide precise request/response shapes. The settings contract explains supported
configuration. These inputs support both human guides and generated reference documentation.

The behavior handoff includes concrete scenarios:

| Scenario | Observable outcome |
| --- | --- |
| A buyer creates an order with two valid items | The application returns an order identity and the expected item totals |
| The buyer retrieves that order later | Stored items and totals remain available |
| A permitted user requests a report | The report follows the application's documented consistency rules |
| Another buyer requests the order | Access is denied without exposing the order's contents |
| A buyer submits an invalid item | Validation explains the problem and creates no partial order |

Each implemented scenario links to its actual interface/test and names prerequisites and relevant
failure states. Documentation writers can turn these into tutorials without interpreting agent
prompts. Roles and sample data are described without publishing credentials.

## Ordinary human engineering

For the existing Foundation consumer profile, these repository-root commands remain usable:

```powershell
./eng/Restore.ps1 -LockedMode
./eng/Invoke-RepositoryVerification.ps1
./eng/Build.ps1 -LockedMode
```

The real application's guide adds its qualified prerequisites, actual artifact locations and
verified local run/review instructions. Final bundle description binds the actual host image
digest through the existing packaging mechanism. Human engineering requires ordinary tools and
application inputs, with no installed AI extension or workflow engine.
