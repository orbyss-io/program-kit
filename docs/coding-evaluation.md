# Coding review and completion

Use [focused guidance](coding-context.md), the selected technology's native checks and ordinary
Spec Kit task/review notes. Current Program Kit phase helpers provide references; they do not
certify source semantics, track engineering checkpoints or generate product acceptance.
Historical `canProceed`, `task_draft.py delivery`, PKC022 claims and fingerprint-bound evaluation
records are not prerequisites for the current native delivery route. Preserve them as history when
present; do not manufacture or translate them into new authority.

## Review the selected behavior

Compare actual implementation with the spec, accepted decisions, plan/tasks and applicable canonical
rules. Cite useful source locations and real consequences. Challenge infrastructure necessity as well
as dependency directions: identify the selected framework mechanism and any concrete unmet requirement
before accepting a replacement project, wrapper, runner or lifecycle. Correct faulty task assumptions.

Use appropriately scoped independent review when available or agreed. State actual authorship and
remaining review limits; do not fabricate a reviewer or infer semantic correctness from metadata.
Relevant effect, trust, lifetime, ownership and failure-path findings remain substantive even when
compilation and tests pass. Small pure transformations need no unrelated review inventory.

## Execute actual checks

Run compiler/analyzers and focused behavioral checks at the first coherent increment, then affected
regressions for changed contracts. Use maintained native verification commands or an existing selected
engineering helper according to its actual CLI. Source/toolchain/configuration, failures, environment
limitations and retained reports should be clear in ordinary delivery notes. Do not borrow results
from different inputs or treat a missing prerequisite, timeout or failed command as success.

For migrations verify native model/snapshot consistency, deploy the actual EF artifact separately,
observe history and durable state independently, and exercise least-privilege runtime admission.
Tests of a handwritten alternative establish neither its necessity nor native EF compatibility.
A deterministic routing fixture proves emitted guidance, not arbitrary agent reasoning or obedience.

## Hand off and obtain agreed review

Describe what changed, why it meets the requested outcome, actual checks and unresolved risks. Keep
remaining work and review pauses visible in the existing task checklist. Only the human's actual
review decision supplies product acceptance; checkmarks, source hashes and a passing script do not.
Honor the agreed boundary before dependent work, preserving explicit scoped deferrals. Use the normal
feature closure checks appropriate to the selected stack; no additional completion receipt or hidden
progress database is required. [Consumer engineering](consumer-engineering.md) owns the common rules.
