# Coding evaluation and completion

Use the existing [context](coding-context.md), [pattern qualification](coding-patterns.md),
native verification and story delivery routes. Preparation lists applicable canonical
`coding.evaluation.duties`; `canProceed` means preparation is ready, not that the code
or product has passed. Mandatory and applicable conditional rules remain due even
when no coding unit or mechanical check was registered for them. Recommendations
remain visible without becoming compulsory.

Each duty names its canonical fingerprint, owner, level, maintainer routing checks,
source review and proof limits. Maintainer checks are not consumer acceptance tests.
Where a requirement needs behavior, actual maintained consumer check evidence is
required alongside scoped authored review. A source-review-only duty may have no
mechanical check; that does not certify its semantics automatically.

## Submit ordinary engineering evidence

Run the existing native Focused/Affected selector and its prerequisite closure for
the actual change. Run only the checks needed by that scope. Preparation, inspection
and binding never execute submitted checks or review files. Native evidence uses
the current verification plan; named toolkit evidence uses its current declaration,
inputs, runner and retained streams. A named check can execute a compiled application
oracle, but remains labelled toolkit evidence rather than a native test-runner count.

In the normal `task_draft.py delivery` engineering/present request, add grouped
`evaluation` claims. This partial example illustrates the shape; cover **every**
required rule returned for the checkpoint's tasks, not just these two identities:

```json
{
  "action": "engineering",
  "checkpoint": "US1",
  "configuration": "Release",
  "checks": ["artifacts/tests/toolkit-runs/<actual-run>/result.json"],
  "evaluation": [{
    "rules": ["principle.compilation-boundaries", "native.allowed-role-references"],
    "checks": [{"kind": "toolkit", "id": "owner-report"}],
    "review": "docs/architecture/owner-report-review.md",
    "conclusion": "The Core row and pure query own their responsibilities; inspect the cited source and independent owner/order controls.",
    "limits": "Finite application oracle and scoped authored review; no provider, browser or human product acceptance."
  }]
}
```

Use an existing ordinary source-review document; no separate approval dossier is
required. The review and conclusion must describe the actual scope and unresolved
limits. Authored claims remain the reviewer's responsibility: their content hashes
do not establish semantic truth or authenticate the author. Source review still
covers mandatory invocation layout, one named C# type per correctly named file,
purposeful XML documentation and member/helper ordering. Compiler/analyzer success
cannot waive those duties.

For native checks, a declaration is `{"kind":"native","project":"tests/Owner.Tests/Owner.Tests.csproj","arguments":[],"configuration":"Release"}`.
Use the exact actual coverage/configuration. Include the referenced execution
artifacts in the handoff's `checks`. Unsupported mechanisms, status-only JSON,
missing outcomes, corrupt streams and replayed results outside their execution
owner reject. Standalone TRX/JUnit reports can describe their actual assertions;
without a maintained current owner they cannot satisfy a mandatory behavior binding.
Native check configuration must match the selected coding context. An evaluated
multi-target source view still does not qualify every target: use actual supported
verification coverage, and retain unsupported target/argument diagnostics from the
native owner rather than inventing a target adapter in this completion reader.

For an operation-level progress checkpoint, the existing `checkpoint` request can
carry the same `evaluation` claims and exact `taskIds`, alongside its usual
`baseline`, `outcome`, `next` and `checks`. Optional `configuration`/`framework`
select the evaluated context when binding. The CLI records current canonical,
source/context, check and review identities inside existing progress state. It
does not create approval authority. Read details through `current --history`.
Later bindings retain earlier progress events; replaced story evaluation remains
in that checkpoint's `evaluationHistory`.

## Completion and freshness

Direct engineering/presentation evaluates the checkpoint's tasks rather than
only the active operation. Ordinary `phase_obligations.py finish` checks completed
tasks; closure and formal handoff evaluate the feature. Direct delivery closure
uses the same boundary. Applicable duties, task scope and source/context must all
be covered by current retained evaluation. Compatible records can cover separate
scopes together. An omitted mandatory duty, changed canonical rule, reviewed source,
configuration or retained check blocks admission with `PKC020` and its actual owner.
Existing pattern incompatibility/staleness and actual-source ownership diagnostics
remain independent blockers with their native repairs. Checked boxes and manual
edits supply no waiver. Failed admission preserves source and completed work.

Review/task checkmarks and retained checkpoint history are excluded from source
identity; they do not make unchanged engineering proof stale. Task-plan headings
and table labels are not evidence of asynchronous `Task` usage. Actual source and
task descriptions still participate in the maintained detector. An explicitly
browser-only scope carries no unrelated native-graph gate; actual changed C#
still encounters Compile ownership and reconciliation.

Run affected checks/review again after a substantive change and record current
claims. Preserve old bindings and failed execution. Native currentness includes
toolchain/environment, configuration/arguments and unresolved failures; toolkit
currentness includes exact declared inputs and both retained streams. Mutable
external-state checks and non-reusable adapters keep the native owner's non-reuse
rules for pattern qualification. An explicitly supplied latest successful native
artifact may instead support an `execution-observation-only` handoff: source,
toolchain, configuration/coverage, reports and unresolved failures must match.
Unknown arguments and unmanaged execution environments still reject. This binds
what executed, without asserting that mutable external state stays unchanged or
making the result reusable qualification. Waiting for human review requires no new
execution unless the engineering basis changes. Local hashes cannot
detect undeclared dependencies or defend against maliciously forged local history.

Engineering handoff, authored source review, toolkit routing and human product
acceptance are distinct. Existing story delivery owns the human decision and
stops charging engineering time while waiting. No additional approval loop is
introduced. Unrelated scopes remain available; shared prerequisites retain their
existing owners. Routing continues to report `applicationObserved: false`.

## Inspect actual contributor proof

Run `python tests/evaluation_review_fixture.py --review` with the prepared
interpreter, preferably through the maintained `validate_coding_evaluation_journey`
check with explicit `--suite Affected`. Its budget is 120 seconds and hard timeout
240 seconds. The new fictional consumer retains commands, both streams, input/source
identities, actual failures and before/after source. Open the printed guide.

The journey compiles the finite owner report and independently rejects an invalid
owner implementation. The supported native adapter executes one actual compiled
oracle suite and reports one suite through the native owner, with reuse disabled;
it is not an xUnit/MTP or provider/browser qualification claim. A disposable canonical role-table mutation changes the task
brief and native check expectation without editing duplicate policy strings,
stales affected qualification and leaves an unrelated browser view unchanged.
Omitted duties, fabricated/replayed proof, incompatible inputs and unowned manual
source fail through actual supported admission. Restored proof reaches engineering
handoff and feature completion after an explicitly **simulated** human decision.
This proves no real human product acceptance, agent obedience or F8 packaged adoption.
Existing F5 native/provider/browser proof retains its original source, scope, failure
and cost records; this journey does not rerun or requalify it. Keep all review material
until the human requests cleanup.
