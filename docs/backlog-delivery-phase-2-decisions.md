## Accepted decisions: round 1

1. Support a reviewed minimal new Azure setup and attachment to an existing project. New setup proposes a private Agile project and required coordination repository. Discover existing configuration and propose only necessary changes. No organization-wide process customization.
2. Automatically discover human-created epics within an explicitly selected delivery scope. Discovery creates review candidates, not approved decomposition or implementation. A dedicated project can use its whole backlog; a shared project needs a narrower boundary. No special tag is required merely for an epic to be noticed.
3. Allow discovery, preparation and proposed backlog mapping while an existing repository continues work under its current authority. Defer that repository's authority switch until active implementation is completed or explicitly paused and handed over. Do not turn local Active status into a cloud execution claim. Handoff is per repository; one repository cannot hold up unrelated participants. Phase 2 activation supports planning, while implementation admission remains unavailable until Phase 4.

## Verified implementation consequences

- Phase 0 uses the existing Azure CLI token facility and is pinned to disposable resources. It is not a consumer identity verifier or authorization service. The product adapter must resolve actual provider identities, keep accountable human and acting identity distinct, and enforce configured decision roles. [Microsoft authentication documentation](https://learn.microsoft.com/en-us/azure/devops/cli/entra-tokens?view=azure-devops).
- Azure branch creators receive explicit permissions including Force push, which also permits branch deletion. Repository inheritance alone does not establish operational-history protection. Inspect the exact branch and distinguish ordinary participating actors from administrators who can change permissions. [Branch permissions](https://learn.microsoft.com/en-us/azure/devops/repos/git/branch-permissions?view=azure-devops).
- Discover concrete project/area boundaries, not a transient board view or an iteration filter. Previously observed items moving outside the scope must remain accounted for. [Area-path queries](https://learn.microsoft.com/en-us/azure/devops/boards/queries/query-by-area-iteration-path?view=azure-devops).
- Phase 1's global native mappings are proposals. Activation requires per-work-item-type fields/states, rule validation and rejection of unresolved placeholders. Native dry-run validation is useful but does not replace revision checks immediately before an approved write. [Type field discovery](https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/work-item-types-field/list?view=azure-devops-rest-7.1), [create validation](https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/work-items/create?view=azure-devops-rest-7.1).
- Bring forward the minimum shared operation journal, conditional dispatch, revision-bound proposals and conservative ambiguous-create recovery from the accepted Phase 0 contract. These are required for Phase 2's writes; richer human-change reconciliation stays Phase 3. Hierarchy creation is a resumable sequence, not a multi-item transaction.
- Extend the product schema with organization/project identity, discovery boundary, verified roles/capabilities, per-type mappings and proposal/operation/adoption records. Keep business milestone meaning distinct from a target date. [Epic and Feature fields](https://learn.microsoft.com/en-us/azure/devops/boards/backlogs/define-features-epics?tabs=agile-process&view=azure-devops).

## Accepted decisions: round 2

4. Use existing human Azure CLI sign-in in Phase 2 and map approval roles to verified individual Azure identities. One person may fill several roles. Defer group expansion, service-principal decision delegation and unattended CI credentials. An agent acts through the verified session identity; it cannot establish approval merely by supplying an actor ID or saying that approval occurred.
5. Define discovery by one immutable Azure project ID and explicit Area Path roots with an include-descendants setting. Default to the project root for a dedicated project. Keep scope independent of team-board layout, sprint and tags; use stable area identities to detect rename/move changes rather than silently widening authority. Cross-project external links remain references rather than another authoritative backlog.
6. Require protection of the operational coordination branch before activation. Permit ordinary conditional commits; prevent ordinary participants from rewriting/deleting history or changing protection. Present exact permission changes in the setup proposal. If the current actor cannot establish protection, retain prepared state and provide an administrator setup action. Preserve administrator recovery access and explicitly bound the guarantee; do not require a PR for every operational record update.
7. Model Phase 2 milestones as named business checkpoints attached to an existing Epic or Feature, with an accountable owner, satisfaction conditions and an optional agreed target date. Store that business meaning in Azure and link participating Requirements while preserving their capability hierarchy. Completion of children does not automatically accept the milestone. General cross-program release scheduling remains outside this phase.
8. Use a separate private Agile test project named `ProgramKit.Delivery.Phase2` in Unfussiness with a dedicated `delivery-coordination` repository and synthetic backlog content. Preserve Phase 0 evidence/resources. Test discovery of unmarked human-style epics, approved decomposition, resume after interrupted writes, concurrent human edits and repeat activation. Discover any matching existing resources before creation and stop on an ownership mismatch. No organization-wide process edits or real business-backlog mutations.
