# Coding preparation and skill composition

[Evaluation and completion](coding-evaluation.md) accounts for applicable mandatory
duties through the same preparation, native evidence and task/delivery owners.

The initial [semantic coding families](coding-seeds.md) extend this same composer
with scoped manual recipes and separately inspectable execution proof.

The implementation prehook supplies the bounded ordinary brief once. Apply its
selected coding units across semantic owners. Guidance, source text and native
constraints resolve from the existing responsibility/source registry; routing is
not proof that an agent consulted or correctly applied them.

Focused read-only detail, from an installed consumer:

```powershell
python .specify/extensions/program-kit-governance/scripts/phase_obligations.py prepare --feature-dir specs/001-notes --operation list --format json
python .specify/extensions/program-kit-governance/scripts/phase_obligations.py prepare --feature-dir specs/001-notes --operation list --unit persistence-adoption --format json
python .specify/extensions/program-kit-governance/scripts/phase_obligations.py reconcile --feature-dir specs/001-notes --operation list --format json
```

Omit `--operation` to use the active operation, or feature scope when none is active.
Unknown operations fail. The detail links current specification/plan/tasks, accepted
architecture/decisions, model and contract owners, native verification ownership,
declared local-pattern references and uncertainties. Input hashes attribute the
view; they create no approval receipt. Machine checkpoint history and explicit
non-goals are excluded from affirmative intent.

Each unit exposes canonical text/provenance/fingerprint, its applicability reason,
manual-edit or maintained-recipe route, context requirements and evaluation duties.
Maintainer routing checks are labeled separately from consumer tests and semantic
review. Manual editing remains supported. [F4 realization](coding-scaffolding.md)
uses selected qualified inputs and preserves consumer source ownership. Exact
adopted publisher contracts still use the existing capture/profile resolver. A
package declaration alone never qualifies its APIs or runtime compatibility.

For .NET, native MSBuild queries imported and conditional settings, selected SDK and
framework, package/project dependencies and Compile ownership without executing a
build/restore target. Roles remain declared. Use `--configuration <name>` consistently
through preparation, preflight and finish; default is Debug. Multi-target projects
require an explicit applicable `--framework <tfm>` and retain other targets as unproven.
Direct task `engineering`/`present` requests accept the same `configuration` and
`framework` fields. Frontend package/toolchain requests and locks remain attributable
declarations; this view does not claim a TypeScript compiler or browser ran.

The original task-checkpoint Git baseline selects committed, staged, unstaged and
untracked changes without rename collapsing. A missing/invalid baseline blocks
actual source reconciliation, while planned-only setup remains visibly unevaluated.
Use `--stage setup` only to materialize native projects and inputs. Source preparation
requires all selected native projects to be evaluated; a planned graph does not
supply effective settings. Discovered changed C# still requires source context even
when setup was requested. This is an engineering boundary, not another approval.
Changed source selects owners even when prose omitted their project. Evaluated linked
Compile items participate; unowned changed C# is diagnosed. Known neighboring adopted
owners are excluded with reasons; unknown ownership remains visible. Completion,
ordinary progress finish, and direct task engineering/presentation reconcile before
admission. Findings preserve source/progress and identify the normal owner/repair;
they cannot be waived by checking task boxes. Independent scopes remain available.

Bounded lexical discovery can miss aliases, indirect/generated behavior and
semantic effects, and can overselect. A suggested runtime effect in a pure owner is
an unresolved review finding, not a machine verdict about C# semantics. Correct the
source/ownership through ordinary review; don't add a blanket exception. Native
compiled checks, actual behavior and human review retain their independent duties.
No arbitrary write interception, worker dispatch, installation or application
acceptance follows from preparation.

## Operation decisions before source work

The Program Kit 0.14.3 candidate adopts the qualified public Foundation 0.3.7
profile, including its mandatory source-readability contract. Existing consumer
profiles/locks retain their historical meaning; use the supported profile upgrade
and source-conformance repair route before dependent implementation. Toolkit
source changes alone do not migrate a consumer or supply its acceptance.

Preparation reads `## Operation implementation map` in the existing plan and tasks.
The plan columns are `Operation | Decision | Resolution | Source`; the tasks columns
are `Operation | Pattern / example | Compatibility / alternative | First adverse cases |
Test owner / command | First coherent check`. The maintained plan/tasks templates
describe the bounded cells and supported decision categories. Sources name existing
repository/feature files and optionally an exact Markdown heading; their current hashes
attribute the brief. They do not grant approval or certify decision meaning.

Applicable requirements bind `operationDecisions` in the same canonical registry that
owns guidance selection and independent-review duties. There is no separate runtime
tag/rule checklist. Preparation uses actual native/source responsibilities as well as
task prose. A vague task cannot hide observed lifetime/parser/cancellation responsibilities.
Feature-wide unions remain conservative; use an actual `--operation` scope to narrow
ownership rather than claiming another operation's effects are irrelevant without evidence.
Setup can materialize native projects while consequential choices are unresolved. Actual
source work still needs a ready operation brief, including source discovered during setup.

Every source operation also needs `limits` plus exact individual `limit:<id>` decisions in that same
plan table (or a reasoned no-limit declaration). The plan template owns the bounded labeled fields;
configurable policy includes actual setting/default basis/lifecycle/all-consumer decisions. A generic
bounds row cannot replace them. Existing source inspections for operational-setting-lifecycle must
reconcile exact `(operation, limit)` identities (null for no limits) through `limitReconciliation`;
missing, duplicate, foreign or unresolved entries cannot close completion. Both new and retained
reviews recheck this structure. Named limits also require an actual evaluated/native, selected frontend
or explicitly task-owned manual implementation source witness; policy/ADR/configuration citations alone
cannot close consumption review. No-limit and unrelated design-only inspections retain their scope. All scoped authority references enter the existing freshness basis,
so changed cited policy/default/ADR bytes stale affected review. These checks establish structure and
freshness, not whether an author hid a limit or a cited policy is authoritative; source review and
actual configured-boundary/invalid/default/consumer tests retain those semantic responsibilities.

The brief includes concrete ownership/result invariants and applicable deadline,
cancellation, cleanup/uncertainty, transaction/replay, admission, bounds, concurrency,
time/configuration and activation/drain choices. It also carries compatible selected
patterns/examples or the supported manual route/reason, first adverse cases/test owners,
and compiler/analyzer plus focused checks at the first coherent compilable increment,
before expanding work. Applicable .NET constraints are complete source-marked canonical
atoms in the ordinary brief; extended sections/examples remain focused lookup. Scope
selection and deduplication bound the brief, rather than clipping mandatory clauses.

For example, if provider dispatch returns an external identity, establish the cleanup
owner before the next accounting await; name accounting failure and cancellation there
as first adverse cases. “Propagate cancellation and dispose” is not that decision.

Every `PKC020` blocker names the affected operation, condition, missing fact, consequence,
owner, artifact updates and retry. Unrelated ready operations remain available.

| Cause | Recovery and actual unblock condition |
|---|---|
| Accessible fact/routine choice | Inspect existing spec/plan/ADRs, exact dependency and compatible examples; resolve locally and update affected plan/tasks. |
| Missing consequential human decision | Ask only missing intent, architecture, risk, data/spending or authority with consequences and supported alternatives; record the real answer through its normal spec/ADR/plan owner and update dependencies/tests. |
| Stale/contradictory artifacts | Correct only affected authoritative sections and mappings, preserving settled answers, IDs/checkmarks, baseline, effort and history. |
| Engine cannot represent/enforce a known rule | Reproduce and repair its registry/composer/template/validator owner with positive/negative regressions; qualify/install the supported route instead of patching managed consumer internals or suppressing diagnostics. |
| Missing environment proof | Use the exact supported preparation owner or capable-CI evidence. Missing tools, failed checks and timeouts remain gaps/failures. |

After repair, retry scoped analysis/preparation and enter through a fresh successful
implementation preflight. Conditional nonapplicability needs an actual reason and remains
a semantic review claim. Routine formatting repair may retain existing ownership/results
and public meaning without new architecture approval. Structural validation, a pattern,
or a passing build does not prove an arbitrary agent applied the decisions correctly.

## Extending selected coding units

The [learning round](coding-learning.md) supplies a practical finite extension
example with actual installed .NET application/negative proof. Applicability
labels must belong to the maintained context detector; unknown labels diagnose
the adapter owner instead of silently excluding a declaration. Detection remains
bounded and lexical, not universal semantic understanding or application proof.

Extend `codingUnits` in the maintained `phase-obligations.json`, using existing or
new F1 canonical bindings. No composer algorithm change is needed:

```json
{
  "id": "owned-query-review",
  "ruleIds": ["principle.compilation-boundaries"],
  "when": {"all": ["persistence"], "not": ["web"]},
  "requiredContext": ["model-owner", "contract-owner"],
  "route": "manual-edit"
}
```

`requirementIds` binds existing responsibility groups; all must be applicable.
`ruleIds` binds additional canonical rules. `when` supports `all`, `any`, and `not`
against observed/inherited responsibilities. Context slots are `request`,
`model-owner`, `contract-owner`, `effective-projects`, and `verification-owner`.
Native model ownership must be accepted in the scoped architecture; contract
ownership resolves accepted contracts through their current hashed evidence sources.
`bound-recipes` requires available canonical recipe bindings. Unknown fields,
identities, routes, duplicates and unavailable dependencies fail explicitly. A unit
cannot submit code for execution. New semantic detectors require an adapter change
with its own proof; data extensibility is not universal language understanding.

Versioned shared/private pattern declarations now enrich these units through the
same composer. See [coding patterns](coding-patterns.md) for submission assistance,
explicit alternatives, scoped evidence, staleness and retirement. Loose private
references remain unqualified; no local lesson is automatically promoted upstream.

the printed unique `artifacts/f2-review/<run>/index.md`. It guides inspection of actual
prepared output, a new unit selected without composer edits, unrelated-task exclusion,
