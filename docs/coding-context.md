Focused read-only detail, from an installed consumer:

```powershell
python .specify/extensions/program-kit-governance/scripts/phase_obligations.py prepare --feature-dir specs/001-notes --operation list --format json
```

Omit `--operation` to use the active operation, or feature scope when none is active.
Unknown operations fail. The detail links current specification/plan/tasks, accepted
architecture/decisions, model and contract owners, native verification ownership,
declared local-pattern references and uncertainties. Input hashes attribute the
view; they create no approval receipt. Machine checkpoint history and explicit
non-goals are excluded from affirmative intent.

Each unit exposes canonical text/provenance/fingerprint, its applicability reason,
manual-edit or maintained-recipe route, context requirements and evaluation duties.
Maintainer routing checks are labeled separately from consumer tests and semantic
review. Manual editing remains supported. [F4 realization](coding-scaffolding.md)
uses selected qualified inputs and preserves consumer source ownership. Exact
adopted publisher contracts still use the existing capture/profile resolver. A
package declaration alone never qualifies its APIs or runtime compatibility.

For .NET, native MSBuild queries imported and conditional settings, selected SDK and
framework, package/project dependencies and Compile ownership without executing a
build/restore target. Roles remain declared. Use `--configuration <name>` consistently
through preparation, preflight and finish; default is Debug. Multi-target projects
require an explicit applicable `--framework <tfm>` and retain other targets as unproven.
Direct task `engineering`/`present` requests accept the same `configuration` and
`framework` fields. Frontend package/toolchain requests and locks remain attributable
declarations; this view does not claim a TypeScript compiler or browser ran.

The original task-checkpoint Git baseline selects committed, staged, unstaged and
untracked changes without rename collapsing. A missing/invalid baseline blocks
actual source reconciliation, while planned-only setup remains visibly unevaluated.
Use `--stage setup` only to materialize native projects and inputs. Source preparation
requires all selected native projects to be evaluated; a planned graph does not
supply effective settings. Discovered changed C# still requires source context even
when setup was requested. This is an engineering boundary, not another approval.
Changed source selects owners even when prose omitted their project. Evaluated linked
Compile items participate; unowned changed C# is diagnosed. Known neighboring adopted
owners are excluded with reasons; unknown ownership remains visible. Completion,
ordinary progress finish, and direct task engineering/presentation reconcile before
admission. Findings preserve source/progress and identify the normal owner/repair;
they cannot be waived by checking task boxes. Independent scopes remain available.

Bounded lexical discovery can miss aliases, indirect/generated behavior and
semantic effects, and can overselect. A suggested runtime effect in a pure owner is
an unresolved review finding, not a machine verdict about C# semantics. Correct the
source/ownership through ordinary review; don't add a blanket exception. Native
compiled checks, actual behavior and human review retain their independent duties.
No arbitrary write interception, worker dispatch, installation or application
acceptance follows from preparation.

## Extending selected coding units

The [learning round](coding-learning.md) supplies a practical finite extension
example with actual installed .NET application/negative proof. Applicability
labels must belong to the maintained context detector; unknown labels diagnose
the adapter owner instead of silently excluding a declaration. Detection remains
bounded and lexical, not universal semantic understanding or application proof.

Extend `codingUnits` in the maintained `phase-obligations.json`, using existing or
new F1 canonical bindings. No composer algorithm change is needed:

```json
{
  "id": "owned-query-review",
  "ruleIds": ["principle.compilation-boundaries"],
  "when": {"all": ["persistence"], "not": ["web"]},
  "requiredContext": ["model-owner", "contract-owner"],
  "route": "manual-edit"
}
```

`requirementIds` binds existing responsibility groups; all must be applicable.
`ruleIds` binds additional canonical rules. `when` supports `all`, `any`, and `not`
against observed/inherited responsibilities. Context slots are `request`,
`model-owner`, `contract-owner`, `effective-projects`, and `verification-owner`.
Native model ownership must be accepted in the scoped architecture; contract
ownership resolves accepted contracts through their current hashed evidence sources.
`bound-recipes` requires available canonical recipe bindings. Unknown fields,
identities, routes, duplicates and unavailable dependencies fail explicitly. A unit
cannot submit code for execution. New semantic detectors require an adapter change
with its own proof; data extensibility is not universal language understanding.

Versioned shared/private pattern declarations now enrich these units through the
same composer. See [coding patterns](coding-patterns.md) for submission assistance,
explicit alternatives, scoped evidence, staleness and retirement. Loose private
references remain unqualified; no local lesson is automatically promoted upstream.

## Inspectable contributor fixture

Run `python tests/coding_review_fixture.py --review` from the feature worktree. Open
the printed unique `artifacts/f2-review/<run>/index.md`. It guides inspection of actual
prepared output, a new unit selected without composer edits, unrelated-task exclusion,
evaluated imports, manual changes and honest failures. Review material remains until
the human finishes inspection. This is installed-layout source proof, not packaged
installation, application execution or agent obedience. See the F2 checkpoint for
actual validation and retained failures/budget limits.
