# Repairing application lifecycle ownership

The lifecycle correction does not change Foundation's runtime contract or consumer
package pins. Existing accepted plans, ADRs, task IDs, ledgers, private configuration,
accounts and databases remain historical authority. Apply an explicit, scoped repair
when an existing application has an unnecessary composition library.

1. Save the current implementation checkpoint and retain unresolved failures. Upgrade
   through the supported Program Kit updater when the correction is published. Do not
   regenerate the consumer's unrelated decisions or substitute the latest dependency
   profile for its captured selection.
2. Read the affected plan and source responsibilities. Look up the exact selected
   contracts with the installed `publisher_knowledge.py --target .` route. Missing
   lifecycle facts require repair of that selected knowledge, rather than a package
   upgrade inferred from today's default.
3. Let each feature register its own services and tasks. Move provider preparation
   into a provider-owned lifecycle contribution. Order required preparation before
   application policy/signing admission and managed worker start using the selected
   lifecycle phases. Preserve async scope ownership, fresh worker scopes, failure
   admission and bounded cancellation/drain. Use an existing lifecycle interface
   before inventing a new Core contract. Domain events describe independent reactions
   to business facts; they do not establish a mandatory initialization chain.
4. Retain a composition preset only for a concrete selection or reuse responsibility.
   Record its rationale in the existing plan/project responsibilities and review
   actual behavior. A passing reference graph does not establish semantic ownership.
   Remove an unnecessary aggregate only after its responsibilities have real owners.
5. Restore and build the affected projects, then package the currently selected roots
   and their exact runtime closures. Use the maintained Build workflow's fresh pack
   inventory. For a pure library with no activatable feature, select its current
   package identity explicitly with `Build.ps1 -RootPackage <PackageId>` rather than
   introducing an aggregate project. Remove obsolete managed feature activations
   explicitly; preserve consumer-owned configuration and deployment data. Run the unchanged published
   Foundation image with the corrected bundle.
6. If test projects were replaced, record `testOwnershipReplacements` in the existing
   `eng/verification.json`. Each row names a retired `predecessor` project and its
   current `successors`. Run fresh, unfiltered successor regressions. The mapping
   preserves original failures and does not grant result reuse or erase history.
7. Run the affected lifecycle, provider, packaging and browser outcomes. Before a
   durability restart, confirm the exact server draft identity, version and content;
   after restart, establish authenticated readiness before inspecting recovery. Keep
   HTTP/status diagnostics free of draft, account and source payloads. A toolkit guard
   fixture is not consumer durability acceptance.

Retain required review findings until the repair and relevant behavior pass. Use the
existing plan, tests and normal review; create no new approval or proof dossier.
Publication still requires the normal dependency review and complete Release gate.
