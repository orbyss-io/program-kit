# Phase 0: technical interview and decisions

Status: Phase 0 complete; decisions 1–11 accepted and validated in the approved disposable scopes. See [results and limitations](delivery/phase-0-evidence.md). All phase work belongs on `codex/backlog-delivery`; commit and push the completed phase after its checks pass.

## Accepted decisions: round 1

1. **Execution model:** deterministic tooling callable from developer sessions and CI, following the existing Program Kit Python tooling approach. Conversational commands guide tested operations. No mandatory always-running coordination service in the initial version; durable shared coordination records may still be required.
2. **Claim guarantee:** one current authorized Program Kit claim among participating sessions, with accountable human ownership and separately identifiable execution. Check changed/lost authority at governed checkpoints. Do not claim to prevent independent human or external-tool code edits.
3. **Concurrent human edits:** preserve human edits. Use conditional provider updates where supported. When a provider cannot protect a shared text replacement, present a proposed replacement through a safer review path rather than silently applying it. Adapter automation levels may differ while preserving governance outcomes.
4. **Edition scope:** prove Azure DevOps Services and GitHub.com first. Record edition/capabilities explicitly. Server-edition support requires separate validation and is not assumed.

The API research identifies a relevant difference: Azure work-item updates support testing the existing revision; GitHub's general conditional-request policy does not support unsafe conditional writes unless an endpoint explicitly provides that behavior. Neither native assignment nor an In Progress status is an execution lock. [Azure update API](https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/work-items/update?view=azure-devops-rest-7.1), [GitHub conditional writes](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#use-conditional-requests).

## Accepted decision 5: code overlap coordination

The user accepted an explicit change-footprint model for affected files/folders and semantic resources, with concise Azure tags/GitHub labels as visible categories. Broad overlap is advisory; confirmed incompatibility requires scoped coordination. Define the common data contract and representative cases in Phase 0, then implement behavior with parallel delivery.

Use native Azure tags and GitHub labels as concise, provider-visible categories, backed by a structured change-footprint record. Suggested display categories include `area:checkout`, `contract:payment-api`, and `coordination:review`. Keep a profile-owned namespace/mapping for generated categories, preserving unrelated human labels. Avoid creating a tag for every file or encoding a complete path list in a scalar tag.

Azure tags are project-scoped categories supporting filters and queries; GitHub labels are repository-scoped and changes do not automatically propagate to other repositories. The profile must map a consistent taxonomy across the delivery space. [Azure tags](https://learn.microsoft.com/en-us/azure/devops/boards/queries/add-tags-to-work-items?view=azure-devops), [GitHub labels](https://docs.github.com/en/issues/using-labels-and-milestones-to-track-work/managing-labels).

Each footprint should identify repository identity, source/base revision, linked plan revision, expected write paths or bounded globs, relevant contract/resource changes, protected assumptions, and the basis/freshness of the assessment. Distinguish planned/inferred scope from observed changed files in a branch/PR. Track read dependencies only when they identify a material assumption; treating every file consulted as a lock target would create unnecessary blocking.

Examples of logical resources include a public API, shared schema, migration sequence, generated artifact source, dependency manifest/lockfile pair, and deployment environment. Different files or repositories can still conflict semantically. Two items mentioning the same module do not necessarily conflict.

Keep dependency readiness separate from compatibility with currently active work. Propose descriptive outcomes such as no known conflict, coordinate before proceeding, serialize a named conflicting activity, or unknown scope. Explain the involved work items, matching paths/resources, evidence, and resolution. These are predictions and policies, not promises of conflict-free execution.

Accepted default: broad path/category overlap is advisory. Confirmed incompatible contract changes or an explicitly exclusive resource require coordination before the conflicting activity begins. Prefer narrowing scope, extracting a shared prerequisite, or sequencing only the overlapping activity over blocking entire requirements. A hard conflict requires an explicit reason; absence of declared scope is uncertainty rather than proof of independence.

Refresh at planning, claim, the already agreed phase checkpoints, and PR preparation, including changed PR head/base or dependencies. Compare actual changes with the declared footprint; material scope expansion triggers reassessment against active work and approved technical direction. Detect incomplete diff coverage, including provider pagination/caps, rather than declaring the visible subset independent. The footprint is a coordination aid, not a rigid file allowlist.

Merge-time validation remains necessary. Where available and configured, GitHub merge queues test the combined changes against the target branch and preceding queued changes. This complements early coordination but does not predict all semantic conflicts or prevent competing implementation. [GitHub merge queues](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue).

Accepted acceptance cases: same-category independent changes remain eligible; overlapping writes raise an explained coordination signal; incompatible cross-repository contract changes are caught despite disjoint paths; generated artifacts are traced to their source; and actual scope expansion refreshes the assessment. No exact line-range prediction, learned conflict model, or automatic merge-conflict resolution is required initially.

## Accepted decisions: round 3

6. **Durable coordination:** an enabled consumer may use a small operational store on its selected platform for claims, operation history, and recovery. Business intent and delivery state remain on the backlog. Adapters may use different native mechanisms under the same tested contract. Local files cannot arbitrate cross-machine claims; no additional hosted service is required. Phase 0 must demonstrate the selected storage and recovery guarantees.
7. **Claim lifetime and takeover:** release claims on normal completion. Display stale activity, but do not automatically reassign work solely because a timer elapsed. The current owner or an authorized coordinator explicitly resumes/transfers abandoned work through a recorded takeover with a new claim generation. Previous sessions detect obsolete authority at their next governed checkpoint. Automatic leases are deferred.
8. **Authentication and attribution:** interactive operations use the developer's authorized identity; CI uses a separately configured application/workload identity. Record the actual actor and accountable human where different. Use supported credential facilities, with credentials outside profiles/evidence. CI write permissions do not confer authority to approve business or architecture decisions.

GitHub's conditional commit input includes an expected branch head, which is a candidate primitive for durable coordination records. It does not make issue edits and coordination commits transactional. Microsoft distinguishes delegated interactive access from application/workload identities for unattended operations. [GitHub conditional commit input](https://docs.github.com/en/graphql/reference/commits#createcommitonbranchinput), [Azure authentication guidance](https://learn.microsoft.com/en-us/azure/devops/integrate/get-started/authentication/authentication-guidance?view=azure-devops).

## Accepted decisions: round 4

Read-only discovery confirmed access to the selected Azure organization and an enabled system Agile process. GitHub organization Projects discovery succeeded and reported permission to create Projects. Available GitHub issue types were Task, Bug, and Feature; Epic and Requirement were absent. These observations establish read capabilities, not successful write authorization or concurrency proof. At that interview checkpoint, no platform resources had been created or modified.

9. **Coordination storage and transport:** recommend a dedicated operational Git repository on the selected provider, using one pinned coordination branch for a delivery space. Azure REST push/ref updates supply the expected previous object ID; GitHub GraphQL `createCommitOnBranch` supplies `expectedHeadOid`. Keep admission state, claim generations, operation intent, and their history in this store; work items remain the business backlog. Shared profiles remain versioned consumer configuration and need not occupy the operational branch. Each admission decision reads the complete relevant state at one head and conditionally commits the resulting change. Recompute after a conflict; never blindly retry the old decision against a new head. Use documented HTTPS APIs for provider operations, obtaining credentials from supported developer or CI facilities.

   This adds repository permissions/setup on both platforms but avoids using a backlog item as a growing operational ledger. Azure work-item revision tests remain appropriate for protecting ordinary backlog edits. A work-item-based coordinator is not the proposed default: per-item atomicity cannot cover claims split across unrelated records, and Azure has a 10,000-revision REST update limit per item. Defer alternate stores until justified. Prove the Git primitives with independent concurrent clients before claiming exclusion. The operational commit and an external issue update are separate effects, never one transaction. [Azure ref updates](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/refs/update-refs?view=azure-devops-rest-7.1), [Azure pushes](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pushes/create?view=azure-devops-rest-7.1), [GitHub conditional commits](https://docs.github.com/en/graphql/reference/commits#createcommitonbranchinput), [Azure work tracking limits](https://learn.microsoft.com/en-us/azure/devops/organizations/settings/work/object-limits?view=azure-devops).

10. **Publication and uncertain recovery:** persist an operation ID, destination, payload fingerprint, approval/input basis and dispatch state before attempting an external mutation. Include the correlation marker in the initial create payload. Confirm and record the provider identity on success. After an ambiguous create response, adopt a uniquely verified matching item or retain `outcome_unknown`; an empty search does not justify another create. Multiple matches require resolution. Resume other independent safe work, but block the affected operation and any dependent completion. Retry creation only when non-creation is established; manual risk-accepting recovery must be explicit and auditable. Preserve human edits, including during recovery. This favors a visible recovery stop over an unsupported exactly-once promise. Both create APIs return provider-assigned identities and expose no documented caller idempotency key. [Azure create](https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/work-items/create?view=azure-devops-rest-7.1), [GitHub create](https://docs.github.com/en/rest/issues/issues#create-an-issue).

11. **Disposable probe scope:** propose a new private Azure Agile project `ProgramKit.Delivery.Phase0`, containing a `delivery-coordination` Git repository and synthetic work items; a new private GitHub repository `program-kit-delivery-phase0` in the selected GitHub organization; and a private GitHub Project `Program Kit Delivery Phase 0`. Test resources must be verified as newly created and recorded by provider ID before probes mutate them. Fail if a conflicting existing name cannot be attributed to this setup. Initialize the coordination repositories during setup. Use synthetic descriptions, comments, relationships, labels, project fields, claims and recovery records. All write/deletion tests stay inside these recorded disposable resources. No shared process or organization issue-type changes, pipelines, paid agent runs, releases, or modifications to existing projects are included. Preserve evidence and resources for review; whole-scope cleanup is a later explicit action.

   Test native hierarchy using available types and preserve canonical kinds in structured records with test-repository labels where needed. Record missing native Epic/Requirement types as a mapping capability gap; do not silently advertise a fully configured default. Phase 5 will settle and validate final GitHub setup/mapping behavior. Two-repository end-to-end delivery remains required in the later acceptance phases; Phase 0 first proves independent-client coordination and provider behavior.

The accepted implementation produces versioned schema examples for the profile/bindings, work identity and authority, observations/accepted basis, proposals/operations, claims, dependencies/evidence and footprints. Include a capability matrix, live probe transcripts stripped of credentials, and deterministic fixtures. Cover conditional-update races, stale claim generations, partial writes, uncertain creation, human edits, incomplete observation and representative overlap cases. Mark simulated failures separately from live observations. Unsupported behavior must yield a recorded limitation or blocked operation. Phase 0 finishes with targeted validation plus the bounded Development suite, then commit and push the phase.
