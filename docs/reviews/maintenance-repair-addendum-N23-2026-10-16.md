## Evidence and cause

The consumer added an API and frontend code consuming newly generated API types. It reports that OpenAPI export requires frontend freshness, while normal composition update compiles the frontend before packing the changed API. Current `artifacts/us3-version-continue/openapi1.log` directly shows successful exact-toolchain/exporter restore followed by `PKC110 frontend inputs changed; build the affected application before run`. There is no traceback or independently executed reproduction in this collection check.

Current canonical and installed `openapi_pipeline.runtime_target` explicitly call `composition_render.verify_outputs(..., check_frontends=False)`. That earlier observation remains correct. The later canonical chain explains a remaining route: `execute_contract` calls `runtime_closure.validate`; it computes `write_value`, then `bound_content`, then `shell_composition.compose_for_stage`, which calls default `compose` with frontend admission enabled. The admission compares current frontend inputs against the prior seal and can raise the observed PKC110. Runtime source freshness also includes frontend files. This is a source-traced failure route consistent with the log, not a recorded runtime call trace. Do not incorrectly attribute the error to the already exempt early `verify_outputs` call or merely add another permissive flag there.

Separately, canonical `composition_run.build` calls `prepare_hosted_pages.build` before package creation/packing. Thus a frontend requiring not-yet-generated types cannot use this ordinary path to first stage the changed producer. Existing full-runtime admission is correct for running/sealing the complete application; using that same prerequisite for producing its upstream contract creates the coupling. Source/API changes still require fresh real producer packages: simply exporting the old staged API would be incorrect.

The consumer proposes preserving exact new UI bytes/hashes, temporarily using the prior working UI to stage the changed API, running actual producer/compatibility/generator, restoring the new UI and rebuilding the full closure. Outcome is pending. This can be a bounded local continuation if every restoration and final guard is actually checked, but it is fragile and must not become the supported default: interruptions must retain exact authored bytes, intermediate runtime must not be presented as current acceptance, and final evidence must bind restored current sources. Collection has not inspected the saved UI or executed the workaround. No handwritten schema/client, receipt rewrite, freshness bypass or baseline advancement is justified.

## Proposed repair and closure

Provide an owned producer build/pack/export contract independent of downstream frontend compilation, reusing selected public exporter and package/architecture/toolchain seams. Bind exact API dependency closure, package bytes, native settings/feature activation needed for actual export, selected shell/provider serialization and version identity. Discover the smallest supported native seam rather than creating a parallel packaging system. An API-only artifact must state its scope and cannot be passed off as a runnable, complete or release-qualified application closure.

Run actual export and compatibility against the retained original baseline, then the maintained client generator, then frontend/application compile and complete current runtime closure validation. Generated client changes remain frontend inputs. Retain strict full admission for runtime activation, final integration and publication; do not route these through a partial-export exception. Intermediate producer work must not require temporarily reverting authored product files or changing human review/accepted architecture authority.

Central installed regression: begin with a valid existing application, add a new typed API plus frontend use that cannot compile against the old generated client, and demonstrate normal producer-first regeneration followed by full build/stage/current-source validation. Prove actual new API output/types and compiled use, not a mocked command sequence. Include a stale/tampered producer package, changed API dependencies/settings/serialization, generator or compatibility failure, stale frontend assets, source mutation between phases and interrupted recovery. Failures must leave authored files and original baselines intact and prevent complete-runtime admission. Show a genuine frontend/test-only change still follows N18's independently qualified ownership rules; separating phases cannot suppress required tests or authorize publication.
