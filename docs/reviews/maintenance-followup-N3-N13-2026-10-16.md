## N3: solution membership can invalidate an unrelated story's review

The continuation diagnostics records D35: adding the later story's worker to the shared solution changed the earlier approved story's review basis. The consumer reports the solution as the sole changed basis input, current complete affected regressions and compiled/runtime evidence, and a native preservation transition under the requesting human's explicit instruction. D37 records two initially rejected request shapes and their correction using supported check records and actor fields. Rejected requests are not waivers or renewed human review.

This is another concrete instance of the existing N3 whole-file projection problem. Extend N3's central two-story fixtures to include an additive solution-member change, not only changes to shared plan/architecture documents. Engineering freshness and outcome review materiality must remain separate.

Critically assess the consumer narrowing: a solution-only edit is not inherently nonmaterial. Establish the actual diff and affected build, dependency, packaging and runtime closure. A new member that changes shared outputs, transitive dependencies, startup, configuration or accepted behavior can affect the earlier outcome. Passing regressions help establish current engineering evidence; they do not alone prove that removing a review input is justified.

The supported repair should retain the original review basis, decision, reviewer and elapsed effort; record the exact nonmaterial assessment and native transition separately under actual human authority. Do not drop all solution files from review scopes, blanket-ignore new projects or rewrite history to imply the original reviewer approved a narrower basis.

**Additional closure cases:** an unrelated additive worker preserves the legitimate earlier outcome approval after current engineering checks; an additive member affecting that outcome's effective closure reopens it; changes to projection rules cannot manufacture approval; the supported transition accepts actual native check records and required actor/source fields with actionable diagnostics for invalid request shapes. Keep the actual consumer review claim separate from central synthetic proof.

## N13: resource ceilings must permit the selected runtime and preserve operational status

The report records D33: the isolated Linux parser failed to load a framework assembly and exited 139 on a known-valid PDF under a 64-file-descriptor ceiling. It reports that changing the descriptor ceiling to 256 allowed the same runtime/input to pass, while retaining the other bounded settings. D34 describes explicit handling of immutable-receipt failure, admission release despite cleanup failure, caller cancellation and pipe overflow. These are consumer execution/implementation observations, not separate Program Kit defects established by this assessment.

Current consumer `PolicyReader.cs` independently confirms a selected `prlimit` invocation with `--nofile=256`, address-space/CPU/core bounds, an outer deadline, and nonzero child exits and internal timeout mapped to `Unavailable`. This is source confirmation only. The reported actual OS-limit and active-process tests were not rerun here; exit 139 alone does not establish its cause without the retained environment and reproduction evidence.

N13 already requires selected-platform execution, demonstrated resource limits, timeout classification and bounded cleanup. Make the result contract precise: runtime startup/assembly-load failure, abnormal exit, deadline and resource exhaustion mean operational/unavailable or inconclusive. They must not be labelled malformed input merely because admission is denied. Caller cancellation retains its separate cancellation semantics. An explicit supported decoder rejection may justify an invalid/unsupported classification only when the protocol supplies trustworthy evidence for that result.

Do not elevate the observed values 64 or 256 into universal requirements. Qualify the actual selected image/runtime and workload under its production-like environment, including cold startup, representative valid inputs and intended concurrency. Observe effective OS limits in the real child and keep input expansion/work budgets distinct from runtime bootstrap requirements. Retain restrictions while adjusting a demonstrably unsuitable ceiling; do not remove isolation to get a green test.

**Additional closure cases:** a known-valid fixture succeeds under the qualified runtime ceilings; startup/assembly-load failure, resource exhaustion, abnormal exit and deadline cannot become invalid-document claims or trigger automatic paid fallback; explicit malformed/unsupported outcomes remain distinct; caller cancellation, descendant termination, pipe overflow, cleanup failure and admission release preserve their documented behavior. Shared examples qualify only their actual boundary; domain-specific reader tests stay in the consumer.
