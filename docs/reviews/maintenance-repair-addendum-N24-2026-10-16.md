## Raw SQL remains a supported design choice

At the 19:26 check, directly read human message `01a145c0-4e18-7a31-9737-5d415442d283`: the user values raw PostgreSQL control and wants explicit method-selection guidance plus a reusable injection-safe, maintainable construction pattern. This clarifies the repair scope: do not turn N24 into a blanket raw-SQL ban or an automatic conversion of every operation to LINQ. Choosing the operation mechanism and owning its identifiers are independent decisions.

Choose EF queries/updates where the selected provider's actual translation, tracking and concurrency behavior meet the operation; choose supported raw SQL when exact PostgreSQL semantics, unsupported translation or demonstrated query-plan/control needs justify it. Do not assume EF is limited to basic operations, or raw SQL inherently improves performance. Inspect the actual generated SQL/plan and preserve the operation's atomicity/locking/replay/deadline contract. Capture the relevant choice in normal source/design review, without adding a mandatory per-query approval artifact.

Microsoft's [EF Core SQL-query guidance](https://learn.microsoft.com/en-us/ef/core/querying/sql-queries) supports SQL where LINQ cannot express the query or produces inefficient SQL, and distinguishes parameterized values from dynamic schema identifiers. Npgsql's [parameter documentation](https://www.npgsql.org/doc/basic-usage.html#parameters) confirms values travel separately from SQL, while table/column names cannot be supplied as data parameters. These current primary documents inform the design; they are not qualification of a new helper against the consumer's exact selected versions.

The reusable owner/provider pattern should keep three inputs distinct: reviewed SQL structure, trusted model-derived physical identifiers delimited by the selected provider, and separately bound typed data values. Use typed mapped-member selection and fail on missing/ambiguous/foreign mappings; do not accept arbitrary request strings as identifiers or concatenate user values. Dynamic ordering/operators need a closed admitted choice, not an escape hatch carrying arbitrary SQL text. Do not interpolate a table-name string through an API that treats it as a data parameter, nor first flatten a safe interpolated value contract into an unsafe ordinary string. Reuse a selected maintained native seam before inventing a parallel SQL framework.

Qualify the pattern with real PostgreSQL: malicious values remain values; attempted identifier/fragment injection is rejected; renamed mapped schema/table/columns propagate correctly; quoted names and mapped property/column differences work; foreign/missing mappings fail; exact locking, JSON, ordering, transaction, cancellation and uncertain-commit semantics remain correct. Share the existing provider connection/unit/transaction and command policy rather than opening unrelated execution paths. Generated/frozen migrations and active SQL syntax/result aliases retain their different ownership. N24's separate accepted-schema conformance check still applies even when every identifier is safely generated. No helper, rewrite or migration is implemented or authorized by collection.
