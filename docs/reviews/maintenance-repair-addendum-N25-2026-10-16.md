## Evidence and attribution

The consumer reports Foundation.Build 0.3.1 emitted EF Design 10.0.13 and tooling dependencies in the packed feature's hostProvidedDependencies even though its PrivateAssets reference was excluded from the nuspec. Correct selected-root runtime staging then failed PKR014. The standard EF Design IncludeAssets selection, which excludes compile but retains runtime/build assets for design-time execution, did not remove the dependency. Original failed descriptors/logs remain retained by the consumer but have not been independently inspected here. Do not claim an independently reproduced exact public-package defect solely from this message.

Direct inspection of the maintenance-owned Foundation checkout `artifacts/fdb-5bda709` at commit `7c209af5d290c98914655b7c0cfb82146bf23efc` confirms the relevant algorithm: EmitFeatureDescriptor reads the first assets target and lists every package with a runtime DLL as hostProvidedDependencies. It does not distinguish ordinary runtime packages, explicit host contracts and design-only dependency reachability there. Source SHA-256 `f9daf8bb08bb3772e8d848433d2d6e9e09e6d01aaecd1372899fdfab38f6ddb4`. This is development-source attribution consistent with the reported failure; exact Build 0.3.1 source/binary identity and target graph still need qualification.

Canonical Program Kit release_bundle reads hostProvidedDependencies as requirements in addition to nuspec dependencies. That explains why omitting a development dependency from the nuspec alone cannot repair a contradictory descriptor. Preserve the staging gate and actual Host closure; do not add design assemblies to the Host merely to satisfy accidental metadata.

[NuGet dependency-asset documentation](https://learn.microsoft.com/en-us/nuget/consume-packages/package-references-in-project-files#controlling-dependency-assets) distinguishes locally consumed assets from propagation to parents: PrivateAssets prevents flow, while IncludeAssets controls consumption. It does not mean a package is supplied by a Host. [EF design-time documentation](https://learn.microsoft.com/en-us/ef/core/cli/services) identifies EF Design as a development dependency, with design services separated from application runtime services. Thus excluding compile alone does not logically remove design-time runtime assets. These primary documents explain the classifications, not acceptance of a specific repaired package.

Runtime provider source no longer declares EF Design, and schema tooling passes an explicit startup project to EF CLI. Separate target/startup project selection is an official [EF CLI seam](https://learn.microsoft.com/en-us/ef/core/cli/dotnet#target-project-and-startup-project). The exact library/startup/factory arrangement, selected tool restore, context/model identity and successful fresh-process commands still need actual execution proof; staging retry remains pending at this check.

This is a plausible bounded separation: runtime features keep their actual runtime dependencies; engineering tools carry design services. It does not repair the publisher's general classification algorithm. Ensure architecture/input ownership admits the engineering project without treating it as a feature/runtime root, pulling its output into public packages or bypassing selected-root closure. Do not copy an alternate design-time model or reconfigure Foundation-owned runtime options to make tooling succeed.

The consumer reports D79 adoption already committed with ten tables' row counts/digests/relation OIDs preserved, and the application Host deliberately stopped pending restaging. This is reported state, not collection-observed preservation or complete schema-semantic qualification. Existing N24/H constraint/index/precondition concerns remain unresolved by those counts. ## Proper shared repair and closure

Foundation owns emitted feature metadata; Program Kit owns consuming closure/admission and actionable guidance. Establish the actual public producer/contract before changing it. Distinguish declared host-provided contracts, packaged runtime dependencies, private runtime requirements and development-only tooling through evaluated NuGet/MSBuild/package metadata and actual dependency reachability. Retain genuinely required runtime packages even when a consumer marks them private; do not simply remove every PrivateAssets package or every dependency also reachable from design tooling. A dependency shared by a true runtime root and a tooling root still belongs to runtime closure. Handle selected TFM/RID and conditional references explicitly; taking an arbitrary first restored target cannot establish all supported target correctness.

Prefer a supported semantic dependency classification/contract over a one-package name blacklist. If a reference's role cannot be established safely, issue an actionable unsupported/ambiguous declaration diagnostic. Preserve missing-host-dependency failure and version/content provenance. Supply selected-version EF tooling placement guidance at the provider/migration authoring point and a maintained executable example, rather than requiring consumers to discover the split after Host shutdown.

Central closure needs real restore/build/pack/descriptor/selected-root installation and Host activation, plus actual design-time context/migration export from the separate project. Include EF Design with normal and compile-excluding metadata, an arbitrary other tooling-only package, true private host contracts, a real private runtime dependency, shared runtime/tooling transitives, conditional/multitarget graphs, missing required runtime libraries and metadata tampering. Prove tooling assets are absent from runtime payload/requirements while correct host contracts remain enforced. Qualify packaging inventory/locks/knowledge and normal upgrade through the eventual public Foundation closure. No descriptor edit, guard bypass, runtime tooling shipment, product change, migration or publication was performed by collection.
