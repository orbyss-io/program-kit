## Lessons for the next item and future development skill

- Investigate existing producers before interviewing. Several choices were routine
  engineering; the useful questions concerned granularity, authority and context.
- Define the visible fixture before implementation. Its independent before/after
  check caught Windows newline changes invalidating unrelated rules; selected text
  now normalizes line endings while raw source hashes retain byte attribution.
- Keep a guided review index and concrete comparisons. A raw catalog/test summary
  leaves the human with too much unexplained output; the index names files, search
  terms, expected failures and proof limits.
- Retain bounded default guidance. Focused source resolution initially made ordinary
  output too long; the existing regression caught it without relaxing its limit.
- Exercise actual installed source dependencies. Resolving sources revealed a
  partial fixture that previously printed summaries without needing those sources.
- Distinguish declaration, structural enforcement and semantic review. A native
  architecture table alone does not establish accepted Core-edge semantics.
- Preserve failed runs and repair their concrete causes. Project-local dependency
  setup, fixture ownership and network restore are distinct from product defects.
- A shared fixture module can select a broad manual downstream check even when
  only its local test setup changes. Its extra packaged evidence was useful here,
  but the measured cost belongs in the next checkpoint discussion. Do not hide an
  overrun or automatically repeat this scenario for every small rule edit.

Carry these observations into F2's interview. Keep the future repository development
skill deferred until this workflow has proved useful across actual items; do not
turn these first observations into universal consumer rules.
