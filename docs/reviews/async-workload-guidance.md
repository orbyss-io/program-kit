# Asynchronous workload guidance repair

## Disposition and evidence

The maintenance disposition is to repair a reusable guidance/discoverability gap, with governance
owning research/semantic guidance and the .NET adapter owning optional conformance support. This is
not a confirmed Docker, Azure, Kubernetes, broker or Foundation runtime defect. No private consumer
was inspected, changed, restarted or used as a fixture. All published examples are fictional.

Source inspection found existing semantic provider, composition and durable integration principles.
However, feature context recognized low-level async/concurrency without a dedicated background-job
research responsibility. The native composition model also selects shell features globally while
environment rows primarily configure supplied resources. Resource settings alone therefore cannot
prove Development/Production package and activation isolation. These are inspected source facts;
they do not establish the cause of an earlier assistant's design decisions.

A bounded open/closed upstream search for asynchronous/provider and Docker/replacement found no
matching issue candidates. Empty search is not proof of uniqueness. Its local correlation record
stays under ignored artifacts. No formal packet import, registered owner-route assessment, consumer
confirmation or public issue closure is claimed from a pasted observation.

## Verification and limits

Use the existing Integrity and Affected suites. The focused deterministic entrypoint is
`python tests/validate_async_workloads.py`; `--compiled` separately builds and executes the .NET
recording fixture. Build failure cannot satisfy behavioral negatives. The compiled check verifies
that Core's resolved dependency inventory is empty. Release build/install/smoke checks inspect the
actual distributed representation. The PR records executed commands, outcomes and local limitations.

The closure checker can establish consistency only with its supplied observations. It does not
discover arbitrary provider activation or deployment rights, establish trustworthy observations,
execute startup or certify platform compatibility. Explicit compatible-pair metadata is a selection,
not qualification. It forbids engine/host privileges outside Development; ordinary cloud IAM belongs
to platform-specific deployment checks. No fallback provider is selected or executed.

The recording fixture's admission/outbox is volatile and cannot prove transactional durability or
restart recovery. Its authority check models resource-side fencing; real storage grants, side effects,
stop confirmation, erasure, outages and partitions need exact provider/version/scope qualification.
Workflow assertions, routed knowledge and static declarations do not establish observed agent
application or human acceptance. No platform SDK/cloud adapter or automatic learning loop is added.

This repairs upstream source only after maintainer review/integration. It does not repair an active
consumer plan. Version remains the unpublished 1.0.0-preview.1 candidate; publication and actual
consumer confirmation are separate outcomes. A later broad knowledge inventory should identify
duplicated manuals and unused captures before removing version facts needed by supported tooling.
