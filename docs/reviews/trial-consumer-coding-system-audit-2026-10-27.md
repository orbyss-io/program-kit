# Trial consumer coding standards and prevention review

The concern has substantial merit. The trial preserves much of Program Kit's compilation and runtime architecture, but several semantic rules have not carried through into the implementation. The clearest problems are repeated string lifecycle values, operation ownership in the API, policy embedded in the persistence provider, implementation-specific policy in Core, incomplete ownership of retained synchronization resources, and browser admission that trusts TypeScript casts. Method coherence is also a real review concern. Widespread failure of the mechanical C# layout rules was **not** established.

This is an investigation and proposed repair sequence. It changes no consumer source, accepted architecture, dependency pins, migrations, task completion or product acceptance. It does not implement the proposed Program Kit changes.

**1. Lifecycle meaning is repeatedly encoded as strings. Confirmed source divergence.** The user's example is representative. `PolicyEvidenceLifecycle.Uploads.cs` tests `policy.State != "Active"`; `PolicyEvidenceLifecycle.Originals.cs` filters policy/document state with the same literal. `PolicyDocumentManagement.Uploads.cs` switches over receiving states; `DocumentRecoveryTask.cs` uses another string comparison; the browser has its own arrays of queued/inspecting/receiving states. Core publishes `string State` in `PolicyUploadOperation` and `string Readiness` in `PolicyVersion`.

The [syntax inventory](../../artifacts/consumer-audit-2026-10-27/source-metrics.json) finds 103 complete C# string tokens matching selected lifecycle words across production/tool source, including 22 `Active` tokens. This is an occurrence inventory, **not 103 independent violations**: fixed wire values and deliberate boundary fixtures require separate classification. Embedded SQL state values and browser strings are additional occurrences outside that count.

The relevant requirements are `principle.lifecycle-language`, `principle.guarded-transition-path`, `principle.solid-design-evidence`, and the .NET profile's instruction to use cohesive owner-specific Constants/keys for lifecycle-bound values. The problem is dispersed semantic authority and weak types, not the mere existence of a string literal. The code already uses enums for several result statuses, demonstrating that typed outcomes are feasible.

Give collection/document lifecycle, upload state, readiness and failure codes distinct owners. Prefer typed states and pure transition decisions inside the application; explicitly map them to unchanged persisted/wire strings. Do not combine every status into one generic enum. Where an external protocol genuinely requires strings, centralize that protocol's vocabulary and reject unknown values at admission. Generate or check browser values against the owned wire schema. Preserve existing SQL representations, API meanings and frozen migration bytes. Prove legal/illegal transitions, unknown-state admission and EF query translation on the actual provider. Replacing literals with constants alone would not supply a lifecycle model.

**2. Several operation methods mix responsibilities and levels of abstraction. Confirmed review finding.** `PolicyUploadEndpoints.AdmitAsync` spans 110 lines and combines identity lookup, precondition parsing, DTO conversion, Core validation, provider availability, parent lookup, command construction, execution and HTTP mapping. Its containing endpoint group has 15 constructor dependencies. `PolicyEvidenceLifecycle.RetryInspectionAsync` spans 120 lines and combines lock acquisition, SQL lookup, replay rules, retry eligibility, capacity rules, state transitions and receipt persistence. `CompleteInspectionAsync` combines publication eligibility, readiness policy, projection changes and database effects. Splitting one partial class across files has not separated these reasons to change.

`principle.method-coherence` explicitly requires one abstraction level and extraction when parsing, policy, mapping or resource ownership becomes an independently meaningful concept. Its suggested validate/prepare/perform/check/return sequence is conditional; it does not require five ceremonial blocks, prohibit guard returns or require every method to have a final success return. The reported methods need meaningful policy/admission/mapping boundaries, not cosmetic sections or pass-through helpers.

The metrics tool records method lengths and syntactic branch signals to locate review candidates. Those signals are **not a certified cyclomatic-complexity measurement**. For example, the bounded Flate decoder is necessarily a detailed algorithm; its branch count alone does not establish an SRP violation. Conversely, a short method can still put policy in the wrong owner. Review lower-level algorithms separately from high-level orchestration and preserve evaluation, transaction and cleanup order while extracting.

**3. The API does not implement the selected operation-local organization. Confirmed source divergence.** There is no `Operations` directory in the API. Route metadata is accumulated in the three partial `PolicyApiFeature` files; create/list/detail/options share `PolicyCollectionEndpoints`; upload/replacement/receive/status/retry share `PolicyUploadEndpoints`; DTOs occupy the project root. Tests are predominantly grouped by subject rather than mirroring individual operation ownership.

Generic vertical slicing deliberately does not prescribe folders. The selected .NET specialization, `principle.minimal-api-operation-ownership`, does: `Operations/<Operation>/Endpoint.cs`, co-located necessary wire/admission/mapping types, small slice-owned mapping methods, and thin feature composition. It permits a reviewed small/bodyless alternative. The inspected design does not justify replacing that arrangement with broad multi-operation endpoint classes. The task plan names project directories and broad filenames, so it made this divergence easy to copy before a useful first operation established the intended pattern.

Keep the correct separate compilation projects. Move actual HTTP operations into their owning API folders, mirror their test ownership and let the feature compose mappings. Preserve route names, schemas, operation IDs and behavior. Shared pure mappings need an explicit owner; sibling endpoints should not call each other's implementation helpers. This is not a reason to add a mediator, generic handler framework or project per endpoint.

Sources: [API composition](../../artifacts/consumer-audit-2026-10-27/snapshot/src/Coverage.PolicyManagement.Api/PolicyApiFeature.cs), [upload composition](../../artifacts/consumer-audit-2026-10-27/snapshot/src/Coverage.PolicyManagement.Api/PolicyApiFeature.Uploads.cs), [collection endpoint group](../../artifacts/consumer-audit-2026-10-27/snapshot/src/Coverage.PolicyManagement.Api/PolicyCollectionEndpoints.cs).

**4. Stable business decisions reside in the PostgreSQL provider. Confirmed ownership divergence; refactoring must preserve atomicity.** `ApplyInspectionFailure` decides transient retry eligibility, retry timing, next operation state, readiness and failure meaning. `RetryInspectionAsync` chooses which terminal reasons permit explicit retry. Those decisions are mixed with EF records, transaction orchestration and SQL. They would have to be recreated or extracted when replacing the provider.

`principle.policy-and-authorization-decisions`, `principle.core-semantic-surface` and the SRP/DIP rules place pure semantic policy at its domain owner. Extract the applicable pure decision over explicit state, admitted policy and decision time. Let the provider load and lock current state, evaluate the decision, enforce atomic preconditions and persist it. SQL ownership, row locks, concurrency and commit uncertainty remain provider responsibilities; moving a transaction into Core would introduce another violation. Simple CRUD transaction scripts remain legitimate and do not need a rich aggregate merely to satisfy DDD terminology.

**5. Core carries implementation-specific concepts and runtime restrictions. The hunch is partly correct.** Core is physically SDK-free, and that is valuable. Semantic independence is weaker. `PolicyBrowserLimits` describes browser canvases, image decoding and retained page surfaces. `PolicyInspectionLimits` includes encoded/decoded stream sizes, decode calls, parser stack depth and stderr bytes. `PolicyInspectionWorkLimits.Validate` imposes `CancellationTokenSource` timer representability and a process timeout-plus-drain lease relationship. A different inspector or execution mechanism would inherit the current implementation's policy shape even if it had different decoding and termination mechanisms.

The issue is not that all limits or validation are forbidden in Core. Positive source length, exact source identity, legal dates, owner binding, complete evidence and an admitted maximum page/byte policy can be meaningful domain or published capability contracts. Pure Core can enforce supplied typed policy. The question is whether each field is a stable semantic promise to accepted consumers or merely today's parser/browser/provider mechanism. BCL-only types cannot answer that question, and the architecture graph cannot detect this semantic coupling.

Keep high-level policy and meaningful execution contracts at their semantic owner. Move browser presentation options and provider-specific decoding/process limits to their actual owners, using a named helper only where a real shared contract justifies one. Enforce native timer/decoder/platform restrictions in the implementing adapter. Do not put configuration I/O into Core, introduce a solution-wide Common library, or assume every duplicate contract needs a new domain/project. Provider replacement remains a design consideration; no alternative production inspector was tested by this audit.

Sources: [browser limits](../../artifacts/consumer-audit-2026-10-27/snapshot/src/Coverage.PolicyManagement.Core/PolicyBrowserLimits.cs), [inspection limits](../../artifacts/consumer-audit-2026-10-27/snapshot/src/Coverage.PolicyManagement.Core/PolicyInspectionLimits.cs), [work limits](../../artifacts/consumer-audit-2026-10-27/snapshot/src/Coverage.PolicyManagement.Core/PolicyInspectionWorkLimits.cs).

**6. Core can silently select operational defaults instead of requiring an admitted snapshot. Demonstrated contract hazard.** `PolicyUploadCommand` accepts optional inspection/work policies and constructs `new PolicyInspectionLimits()` / `new PolicyInspectionWorkLimits()` when omitted. Operational defaults are repeated in Core, runtime settings and inspector input options. This gives more than one place authority to choose a budget.

The exact-source [.NET configuration probe](../../artifacts/consumer-audit-2026-10-27/core-probe.sdk402.stdout.txt) binds a 15-second wall deadline through configuration. Explicitly passing that snapshot gives the command 15 seconds; omitting it silently gives 60 seconds. The same probe confirms nondefault upload byte/page limits and canvas pixels flow through the actual settings readers. This is not proof that the present HTTP path ignores configuration: `PolicyUploadEndpoints.AdmitAsync` explicitly supplies both admitted snapshots. It is proof that another valid caller can bypass their selection through the public Core constructor.

Require the complete admitted policy at work admission or let the application owner supply it through its actual configured capability. Avoid optional operational defaults in a supposedly already-admitted command. Keep one authoritative default source per policy; a missing persisted or process snapshot must fail rather than inherit a current default. The existing `PolicyInspectionSnapshots.TryRead` already does useful completeness validation for durable snapshots and should be preserved.

**7. Configuration is substantially implemented, but some effective limits remain scattered. Confirmed mixed result.** The application uses the selected shell's `IConfiguration`, typed settings, activation admission, restart-bound immutable values, source-backed settings metadata and persisted work snapshots. Upload, input, inspection, work, read and viewer settings have real readers. The absence of a consumer-owned `appsettings.json` is not a defect in a Foundation-hosted application; effective host/shell configuration is the relevant authority.

The remaining examples include the worker's `FindRecoverableUploadsAsync(64)`, the provider's separate maximum-of-64 guard and claim `.Take(64)`, browser 30-second JSON calls, 750/1000 ms polling, unbounded total observation loops and independent default copies. Some may be justified fixed engineering safeguards. They must be classified and owned, rather than automatically made configurable or assumed to be accepted business policy. The exposed `VisiblePages` setting has no frontend read; the current viewer renders one page, so this is not evidence it exceeds the maximum. Its advertised semantics should be clarified or the unused setting removed.

Do not put invariants such as exact ownership, page/hash identity, legal state transitions or citation integrity into adjustable configuration. For legitimate adjustable policy, test omitted/default, nondefault, invalid and exact boundaries through actual activation and all consuming paths. The compiled configuration probe exercises actual source readers with an in-memory `IConfiguration`; it is not a new host activation test. Existing broader activation claims in tasks were inspected, not rerun.

**8. Resource ownership and retained synchronization state are incomplete. Confirmed source gap; exhaustion was not induced.** `PolicyTextInspection` is a singleton that owns a global semaphore plus retained owner/source semaphore dictionaries but implements no disposal path. `PolicyOriginalRoot` intentionally retains per-source `LocalOriginalGate` objects for a generation; each gate owns a semaphore and cancellation source. Root teardown releases the exclusive file handle after actual use finishes, but does not dispose the gates or its shutdown cancellation source. These collections have no explicit retained-identity bound.

The creator/disposal and retention rules apply. This does not establish an operating-system handle leak for every semaphore: `SemaphoreSlim` need not allocate a wait handle. It establishes missing ownership completion and growth with distinct identities. ConcurrentDictionary factories can also allocate losing disposable values; that path deserves explicit treatment.

Preserve the correct security invariant: never reclaim a gate while an old waiter or actor can resume and evade its fence. Add an owned stop/admission/drain/disposal sequence and either a safe reclamation protocol or a justified retained-state bound. Dispose only after actual users and callbacks finish. Test partial initialization, concurrent disposal, late waiters, canceled acquisition, old-source reuse and repeated generations. Do not fix this by blindly removing a dictionary entry after its active count reaches zero.

Sources: [inspection owner](../../artifacts/consumer-audit-2026-10-27/snapshot/src/Coverage.PolicyManagement.Pdf/PolicyTextInspection.cs), [root owner](../../artifacts/consumer-audit-2026-10-27/snapshot/src/Coverage.PolicyManagement.Documents.LocalFiles/PolicyOriginalRoot.cs), [source gate](../../artifacts/consumer-audit-2026-10-27/snapshot/src/Coverage.PolicyManagement.Documents.LocalFiles/LocalOriginalGate.cs).

**9. Complete deadlines and replaceable time are inconsistently carried. Confirmed source divergence; no live overrun measurement.** Native PostgreSQL units supply deadlines, and uncertain create/upload reconciliation correctly reuses the original unit deadline. Durable queue/lease expiries are also preserved. However, multi-effect application operations pass only a caller token across successive fresh database units; they do not establish and carry one outer `IExecutionDeadline`. `FindRecoverableUploadsAsync` performs follow-up operation reads with the original caller token, allowing each read a fresh unit budget.

The file root and PDF adapter calculate expiry from `TimeProvider`, then use ordinary `CancelAfter`, which uses the real timer clock. The root's drain `WaitAsync` similarly lacks the selected clock. Some provider admission paths read `now` before subsequent lock/query waits and use it for later decisions: upload admission reads before the global/parent locks; inspection claiming reads before candidate discovery and locks. `OriginalGrant` and final publication have additional fresh-time checks, so this audit does not claim those stale reads prove unauthorized Ready publication.

Apply `principle.runtime-time-and-io`, `principle.decision-time-budget` and the existing implementation-boundary guidance. Use one complete execution budget per bounded operation, capped stages, provider-aware timers, and fresh effect-decision reads after waits. Preserve distinctions between human interaction, durable workflow lifetime, one execution attempt and cleanup ownership. A browser must not keep one request open for a ten-minute workflow merely to share a deadline. Test actual lock-wait expiry and distinguish caller cancellation, deadline expiry, actual stop and uncertain commit.

**10. Browser runtime admission does not uphold the selected TypeScript rules. Demonstrated.** `response<T>` returns `received.json() as T`, and the upload XHR resolves `JSON.parse(responseText) as Operation`. A generic type argument supplies no runtime validator. Antiforgery helpers check a truthy token but do not check its string type. Generated API declarations are useful compile-time contracts; they do not validate incoming JSON.

The [offline browser probe](../../artifacts/consumer-audit-2026-10-27/browser-probe.results.json) accepts a valid control, then demonstrates that `readPolicy` accepts `{ completelyWrong: true }`. With mocked fetch/XHR, `receiveFile` sends a numeric antiforgery token and accepts `{ unrelated: true }` as an operation. This proves the client admission paths, not that the server accepts an invalid token or that a real cross-owner request succeeds. The functions are taken from the retained snapshot; only the error class's TypeScript parameter-property syntax is desugared for Node, and network/browser primitives are fictional.

Use runtime validators owned by the actual wire schemas, tolerant of permitted response evolution but strict about identities, required fields, sizes and known variants. Share the application-owned BFF token adapter instead of repeating differently strict parsing in collection and document clients. Preserve the server's independent authentication, CSRF and owner checks. Add malformed/null/wrong-type/oversized/wrong-identity response tests around actual client functions, not just TypeScript compilation.

Sources: [browser client](../../artifacts/consumer-audit-2026-10-27/snapshot/web/src/api/client.ts), [document client](../../artifacts/consumer-audit-2026-10-27/snapshot/web/src/features/documents/api.ts).

**11. Browser execution, cancellation and formatting need stronger ownership. Source finding.** JSON calls each create a new 30-second timeout; token acquisition plus a command can therefore restart the budget. XHR registers `ontimeout` but never assigns a timeout. Original PDF fetch/body reading relies on caller cancellation with no own elapsed deadline. Upload observation polls until an observed terminal string with no overall observation policy. `SessionProvider` removes handlers on unmount but does not abort already-started reads or bound concurrent refreshes; sequencing prevents stale results from winning, not the work from running.

The product has an explicit draft/job owner and many abort paths, which should be retained. Distinguish durable server work from bounded network actions and give each browser action an explicit cancellation/deadline/observation owner. Unconfirmed transfer must preserve reconciliation data. The `web` package exposes TypeScript `check` and `build`, but no inspected pinned lint/format task/configuration. Dense JSX and statement packing therefore lack a reproducible frontend style check. The .NET one-type-per-file rule must not be silently applied to TypeScript.

**12. Several implementation helpers are public, and construction still performs filesystem observation. Source divergence.** Runtime classes such as `PolicyDocumentManagement`, `PolicyEvidenceAccess`, the workers and `PolicyTextInspection`, plus pure implementation helpers such as `PolicyJsonCapacity`, `PolicySourceCapacity` and `PolicyInspectorProtocol`, are public. Some helpers are directly consumed by tests. Public feature activation types, public wire contracts and types genuinely required by a selected framework need separate treatment; a blanket public-type ban would be wrong. Existing instructions specifically default private implementation helpers to internal and reject exposing internals solely to rescue tests.

`PolicyOriginalRoot` construction creates `LocalOriginalPaths`; that constructor calls `Check`, which observes filesystem attributes. Root exclusivity is correctly acquired later in Prepare, but path preparation still hides fallible I/O in construction, contrary to `principle.construction-invariants`. Move physical admission to its explicit lifecycle/factory owner; pure canonical path calculation can remain construction. This does not call for a factory interface for every object. The guarded `PolicyCreateResult` and `PolicyInspectionResult` factories are good existing examples and should be preserved.

**13. Product worker failures lack a bounded observation channel. Source gap.** Recovery and inspection workers catch classified availability/original failures silently. No application `ILogger`, `ActivitySource`, `Meter` or equivalent product instrumentation was found under `src`. Native HTTP/task infrastructure and durable operation rows provide some observation, but they do not by themselves explain repeated swallowed storage failure, cleanup backlog or stuck recovery. Define safe event codes, low-cardinality metrics and correlated operation identities without filenames, document text, paths, credentials or raw parser diagnostics. Test failure observations and redaction. This follows the existing async-operation and observability rules rather than requiring a new telemetry platform.

There is an important distinction in rule strength. `principle.operation-owned-api-source` and `principle.minimal-api-operation-ownership` explicitly require operation-local API placement with a proportional small/bodyless exception. The generic vertical-slicing guidance explicitly leaves physical layout to the project. The inspected broader guidance does not establish a universal folder tree or a maximum number of root files. Therefore the API arrangement is a concrete conformance divergence; the other flat roots are an evidenced maintainability problem and an insufficiently specified project convention, rather than violations of a nonexistent blanket folder rule. A three-file Web project may reasonably remain flat.

An appropriate placement proposal for this consumer is:

| Owner | Useful organization to review | What remains near the project root |
| --- | --- | --- |
| Core | Cohesive Collections, Documents/Versions, Uploads, Evidence and OriginalAccess groups; keep the actual semantic capability with its associated request/result/policy types | Project declaration and genuinely project-wide entry metadata; first remove misplaced provider/browser concepts rather than hiding them in a folder |
| Runtime | Collection operations, Uploads, Inspection and Recovery; co-locate each operation's policy/orchestration and necessary private helpers | Feature registration/composition and source-backed settings metadata; place settings with their consuming responsibility where practical |
| API | Operations/CreatePolicy, ListPolicies, AdmitUpload, ReceiveUpload, ReadSourcePage and the other actual operations, with necessary request/response/admission/mapping files | Thin feature composition and genuinely shared transport policy with an explicit owner |
| PostgreSQL | Collections, Documents, Uploads, Inspection, OriginalAuthority and Schema groups containing their provider-owned records/query/effect code; retain native Migrations ownership | Thin provider registration and native project/metadata inputs |
| LocalFiles and PDF providers/tool | Small groups for actual custody/access, execution/supervision, protocol admission and decoding responsibilities where these improve navigation | Thin activation or process entry point; avoid a deep hierarchy for the small LocalFiles project |
| Tests | Mirror the operation/capability being tested, with narrowly named shared fixture/support folders | Test project declaration and genuinely assembly-wide configuration |

These are proposed responsibility groupings, not instructions to create every named directory or a new project for each folder. Avoid generic catch-all Helpers, Managers, Models or Utilities folders. A type's semantic owner, closest actual consumers and reason to change should explain its placement. Preserve the accepted compilation boundaries; an operation's API, Core and provider files can mirror ownership across separate projects without bringing implementation references together. Moving files alone does not separate a broad partial class or repair policy placement.

There is also a concrete producer inconsistency. The current optional `typed_operation.py` adapter writes each example file to the selected project file's parent directory. An actual read-only render with fictional owner paths emits LabelEndpoint, LabelEndpoints, LabelRequest, LabelResponse and LabelApiOptions directly under the API project root, with no Operations subfolder. Its existing scaffolding test also indexes the root destination. The [render observation](../../artifacts/consumer-audit-2026-10-27/file-placement-recipe.json) preserves those actual destinations. This conflicts with the more specific operation-placement guidance and makes a flat layout an easy example to copy. It is not evidence that this consumer invoked that adapter, and a narrow recipe's exact output remains its own current contract until repaired through the owning producer and tests.

Prevention should cover placement before the first pattern is replicated: agree a small project-local responsibility tree in the ordinary plan, place the first operation and its test there, and inspect whether a maintainer can locate the request, policy, effects and adverse tests from that tree. Align the existing .NET example/adapter and its tests with the selected API convention. Extend normal source review to challenge unrelated new root files, without inventing an arbitrary root-file quota or requiring a folder for each type. Outside the API specialization, document a proportional project convention rather than claiming the toolkit already mandates this exact tree.

Any eventual move must reconcile explicit source paths, source-backed settings hashes, project includes, task/document links, engineering source inventories and tooling assumptions. Keep operation IDs, public namespaces/contracts where compatibility requires them, migration identities and observable behavior stable. Compile and run affected checks for actual moves. This research update moves no consumer files and executes no consumer build or application suite.

**SOLID assessment.** SRP is the strongest confirmed concern: grouped endpoint owners, mixed operation methods, and pure retry/readiness policy inside EF effects. DIP is partly upheld by separate projects and semantic ports, but weakened by implementation-shaped Core contracts and configuration-default construction. OCP is upheld in many native extension uses; duplicated former asset/presentation infrastructure shows a prior missed extension point. ISP warrants review of `IPolicyEvidenceLifecycle`, which currently exposes collection creation, store binding, original authorization, upload recovery and inspection work through one interface to different audiences. Its size alone does not prove a violation: split only where consumers, security, consistency or replacement ownership differ. No concrete LSP/substitutability failure between two production providers was established. Do not mark all five principles failed or add an interface per method.

**Domain seams and events.** The separate Policy Management and Claim Assessment ownership is explicit in the ratified constitution, ADR and map. Current source implements Policy Management; the absence of Claim Assessment or its evidence bridge is not a current boundary violation. No peer-context database access or implementation project references were established in the reviewed source. The accepted future synchronous evidence capability/consumer-owned bridge is appropriate when assessment needs an authorized answer.

No current independent business observer was identified that makes a domain event mandatory. The upload/inspection pipeline needs ordering, persisted authority, retries, results and actual cleanup. Replacing those calls with an in-process event would weaken the contract.
