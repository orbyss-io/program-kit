## Why the earlier passing rehearsal did not cover this failure

The earlier rehearsal used a narrower capture/read outcome and did not exercise the
actual consumer's retained EF/Npgsql/PostgreSQL compatibility condition. The actual
intake chose private access, capture, shared view, bought and undo as the first outcome,
plus separate future repeat, history and offline journeys. This replay preserves those
answers and seven immutable source journey IDs; it does not reduce scope to obtain a pass.

Three product gaps were repaired:

1. **A test-only database pin never reached the consumer.** PostgreSQL's exact image
   existed in test service configuration while installed persistence guidance exposed
   only EF/Npgsql/Testcontainers package pins. The installed persistence runtime reference
   now supplies PostgreSQL 18.6 and its immutable image digest. Research and closure
   receive it through the existing provider projection. Package versions still come from
   the existing profile props, and explicit SQLite/SQL Server choices are not overwritten.
2. **Managed publisher evidence was left for each consumer to reconstruct.** Research
   could guess the wrong Foundation repository URL or treat a missing GitHub Release
   page as missing publication. The installed, dated evidence inventory now binds exact
   publisher source, registry image, package metadata, distribution notices and successful
   publication workflow. The compact projection exposes it before architecture selection
   exists. A different Foundation version requires renewed evidence. Source admission and
   runtime compatibility remain distinct; a runtime pass never closes a license question.
3. **Roadmap authoring contradicted first-feature handoff.** A combined approved
   `first_slice` needs one entry whose Scope contains every selected canonical candidate.
   The old instructions encouraged one entry per journey, allowing four entries plus a
   sentence saying they shared a specification. Roadmap now receives the exact candidate
   IDs and explicit combined-boundary rule. Its terminal validation checks that handoff
   before synchronization or any compatibility execution. Future journeys cannot be added
   to the first entry, and no existing approved boundary is silently narrowed.

The new maintained `ef-postgresql` recipe reuses the shared toolchain and renew/locked
restore coordinator. It builds an isolated synthetic EF model and checks the running
server version, write/read, atomic stale-revision rejection, transaction rollback and
state after server restart. It uses an ephemeral loopback port and disposable credentials,
cleans up its own container/volume, and produces named JUnit cases. It creates neither
consumer application targets nor a production migration policy.
