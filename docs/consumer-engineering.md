# Consumer engineering

Program Kit contributes relevant knowledge to native Spec Kit phases. Product intent,
constitution, ADRs, a small domain/C4 map, roadmap and ordinary spec/plan/tasks documents
hold the useful authored decisions. A fresh intake can use existing architecture files.

Agree meaningful human review points before implementation and make them visible in
the plan/tasks. Stop at an agreed point and obtain the human's decision before dependent
work continues. Record that outcome in readable review/progress notes. Do not fabricate
human acceptance, infer it from tests, or introduce a hidden checkpoint ledger.

Missing toolkit status files, approval fingerprints and historical workflow receipts
are not independent prerequisites for coding. Revisit a changed product or architecture
decision through normal review. Preserve unaffected work. Real unresolved decisions and
actual engineering failures still need resolution in their dependent scope.

Specify owns observable behavior; planning owns the research that justifies technical choices.
The existing after-plan architecture review examines the actual feature documents and accepted
architecture, explains alternatives and source/version applicability, and resolves material open
choices before dependent tasks. A reference index supplies context, not that semantic review.
Keep consequential decisions and their reasons/checks traceable in ordinary research, plan or ADR
sections; tasks carry the selected responsibilities, pattern commitments and adaptations forward.

During coding, read the task's behavior/owner/decisions and relevant source, consult focused guidance
and exact dependency facts, then implement/check the smallest coherent case. Review actual source
against the chosen semantics before replicating a new or uncertain approach. Private file/class
details can evolve while accepted responsibilities, contracts and failure semantics remain intact.
Use the shared [engineering feedback method](../extensions/program-kit-governance/references/engineering-feedback.md)
for discoveries that change product behavior, assumptions, contracts or task dependencies. Correct
the owning documents and affected work openly, preserve unrelated decisions/completed tasks, and
rerun relevant review/checks. Native Analyze reports first and stays read-only; any authorized
repair is a separate explicit step. A proposed ADR supplies no human-approved override.

Select technology guidance and automation proportionally. The recommended stack has a
convenient default engineering route. A user can choose another technology or build
approach, document the choice and run its actual checks. Optional generators/runners
validate the inputs needed for their selected operation; their configuration does not
become a prerequisite for using knowledge. Starting an entire application is not a
universal before-coding step.

An accepted maintained Foundation composition should have one explicit first engineering increment:
active graph, exact pins and generated configuration. Include realm/login checks only for selected
identity, product permission/owner checks where applicable, and native schema deployment/read-only
admission plus a small real provider fixture for selected persistence. Do not introduce identity or
a database into an unrelated composition. Reuse that fixture without repeating the Host/identity suite.
This normally belongs in the first feature, not a mandatory separate setup spec or human gate.

Make large tasks executable as small observable increments with actual prerequisites. Compile the
first integration against known local APIs before replicating it; pair meaningful expected red tests
with implementation and add all agreed adverse cases before claiming readiness. Implement settings
beside their first consumer and reconcile the full inventory at closure. Preserve safety invariants.
After an authorized architectural correction, reconcile operative task wording/dependencies while
preserving IDs, completed work and history. Keep concise current status and links to prior evidence
in the existing documents. Continue authorized ready work until an agreed review, genuine blocker or
completion; saving progress alone adds no pause. Test counts and task counts do not measure delivery.

Source, tests, native project/package files and locks, selected eng/deployment inputs
and CI enforce the software. Compiler/analyzer diagnostics, meaningful architecture,
security and behavioral checks retain their actual authority. A structural graph check
does not prove semantic ownership; tests do not supply human product acceptance.
Program Kit need not be installed to build or deploy the resulting application.

Review the first coherent source before replicating its pattern: method abstraction, typed state
ownership, pure policy/provider separation, effective configuration and admitted snapshots, complete
deadlines and actual resource teardown. Establish navigable project-local placement and mirrored
test ownership at that increment, preserving compilation boundaries and proportional small projects.
Correct applicable source findings then; final settings/SOLID reconciliation is not permission to
repeat them. The canonical programming guardrails and selected technology specialization own the
details. These are source-review obligations, not a new approval ledger or an automatic semantic gate.

Generated diagrams, focused guidance and local check output are regenerable views.
Keep one useful source for architectural meaning rather than maintaining duplicate
approval projections. Version-specific publisher knowledge and SDK contracts remain
relevant when that exact dependency is selected.

The 0.x-to-preview boundary requires fresh product intake, using selected existing
architecture as input. Preserve application source, native Spec Kit artifacts, ADRs,
locks and user customizations. Do not translate old workflow state into new authority
or delete arbitrary historical files. Future previews preserve authored ongoing work;
a later break requires explicit notice. Installation ownership and archive-integrity
checks protect toolkit replacement and are separate from authoring state.

Device/global tools are prepared by the human using the presented platform-appropriate
script. Agents may restore declared project packages with existing installed tools.
Optional paid workers, provider access and publication retain their separately scoped
human authorization. Ordinary Spec Kit phases do not invoke them.
