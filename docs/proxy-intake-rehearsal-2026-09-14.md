# Optional proxy intake and first rehearsal

An explicit user request now enables `speckit.program-kit-governance.proxy-intake`.
The command uses the current assistant as interviewer and disclosed fictional consumer proxy.
It defaults to one question round for a quick scan; full intake stops at a validated draft.
It reuses the installed intake method, defaults, authoring schema and validators. It starts no
additional coding agent and supplies no confirmation, bootstrap, implementation or release authority.
See the [command](../extensions/program-kit-governance/commands/speckit.program-kit-governance.proxy-intake.md).

The disposable workspace records scenario-bound proxy provenance before authoring. The ordinary
confirmed-intake validator and bootstrap lifecycle entry point reject a workspace carrying that
marker. The marker is provenance and an accidental-promotion guard, not a security boundary against
someone deliberately removing or copying artifacts. A real human intake remains separate.

## Household shopping rehearsal

These are simulated examples, not consumer truth or future acceptance-fixture expectations.
The user authorized a full draft intake and explicitly required stopping before bootstrap.

| Question | Simulated answer |
| --- | --- |
| First useful outcome? | Record a shared need and let both partners see it; bought handling follows. |
| Participants and rights? | Two private partners with equal editing rights; no public signup. |
| Initial surface and offline needs? | Phone-friendly browser, online initially. |
| Ongoing list or shopping trips? | Ongoing needed/bought list; mistaken bought marks can be undone. |
| Automatic merging or shopper claims? | Neither; keep independent additions visible and avoid promising prevention of every duplicate purchase. |
| Save failures and overlapping edits? | Visible pending/failure/conflict states; acknowledged updates survive reload. Exact criteria belong to the affected specification. |
| Private access? | Individual sign-ins followed by consumer-owned household membership checks. |
| Future order? | Common-item reuse and purchase history remain separate journeys; propose reuse first. |
| Honest historical coverage? | Only retained purchase facts; fictional demo reset may discard them. Real retention rules wait for deployment review. |

No additional constraints were supplied. Local Program Kit defaults remained usable, including
Foundation/.NET, BFF/local Keycloak, the applicable EF/PostgreSQL persistence profile and UI profile.
Provider admission, exact pins, production costs and hosting were not researched or approved here.
The draft proposes one Household Shopping business context, conceptual list/recall/access modules
and three founding decision candidates. Seven journeys preserve recording, remaining-list reading,
bought handling, reuse, history, sign-in and undo separately. This is intake discovery, not a committed
seven-specification roadmap; architecture must evaluate useful grouping and dependencies.
