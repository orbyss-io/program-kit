## Architecture context

Name the domain owner, affected boundaries, public contracts and important quality requirements.
Use existing product intent, intake and relevant ADRs when available; a roadmap is an optional
planning aid. A useful specification can proceed without toolkit identity fields or approval hashes.
Clarify material product ambiguity and preserve supplied rules, rationale, examples and exclusions.

For affected UI journeys, link the current reviewed design when available and reuse its agreed
observable experience. Distinguish illustrative mock content from product requirements; resolve
consequential contradictions through the existing design conversation rather than silently redesigning.

Keep native prioritized user stories, independent tests, Given/When/Then scenarios and measurable
success criteria. Include material failure and boundary cases. Describe observable behavior here;
leave technology/test-framework choices to the plan. Retain applicable tests required by the
constitution and agreed human review points. Split oversized work by useful actor journeys, with
necessary ownership, authorization, persistence and recovery, rather than technical layers.
