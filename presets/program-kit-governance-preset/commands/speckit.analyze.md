## Program Kit operation dependency analysis

**Ordering precedence**: This section takes precedence over task-ordering examples in the
upstream Inconsistency pass (F), including integration before foundational setup. It changes
only that ordering interpretation. Retain every other upstream analysis step, detection pass,
coverage mapping, severity rule, constitution authority, report and remediation boundary,
and `hooks.before_analyze` / `hooks.after_analyze` dispatch. Analysis remains **STRICTLY READ-ONLY**
and requires complete `tasks.md`; neither a draft nor a readiness result proves product acceptance.

Read the resolved operation-based tasks template and the `Operation dependency map` and
`Task dependency map` in tasks.md. Judge ordering by those exact dependencies and approved
spec/plan/constitution obligations, not phase names, layer names or task IDs alone. An independent
first operation may integrate before unrelated future foundation work. Do not report that as
an inconsistency or restore a blanket foundation barrier. Minimal enabling work belongs beside
the first operation that needs it; shared prerequisites gate only their named consumers.

Still report missing named prerequisites: authorization, security, ownership, storage/migration,
real-provider tests, risk-selected verification, contracts, admission and retained authority/approval gates. Report
unknown task IDs, missing map rows, dependency cycles, contradictions between maps and tasks,
and an operation scheduled before a prerequisite it actually requires. Cite the affected
operation, task IDs and spec/plan/constitution requirement; do not replace a concrete finding
with a generic requirement to finish every foundation task. A map cannot waive a mandated gate,
an unresolved product-specific ownership/replay/recovery test, or a due roadmap prerequisite.
For legacy tasks without maps, derive only dependencies supported by their approved artifacts;
report unclear or missing dependencies without inventing a universal foundation phase.

For example, owned create/list can precede later upload storage and OCR infrastructure when
its own authentication, ownership, persistence and real-provider prerequisites are established.
Missing its required authorization or provider proof remains a finding. An upload operation
requiring that storage cannot precede it; an OCR operation cannot bypass its admission gate.
Report planning coverage separately from actual executed proof: finalized tasks,
unchanged setup readiness or a focused checkpoint never establish full product acceptance.

Compare both existing `Operation implementation map` tables. For each affected source operation,
confirm concrete ownership/result invariants and its applicable cancellation/deadline,
cleanup/uncertainty, transaction/replay, admission, bounds, concurrency, configuration/time and
activation/drain choices. The task row must select a compatible pattern/example or supported manual
route/reason, name first adverse cases and their actual test owner/command, and place compiler/analyzer
plus focused checks at the first coherent compilable increment before expansion. A generic “follow
guidance”, a list of rule IDs or an empty decision is a scoped finding. Judge decision meaning and
explicit conditional nonapplicability against actual source/rules; structural presence proves neither.
Each blocker names affected operation, condition, missing fact, consequence, owner and recovery:
investigate accessible facts; ask only missing consequential human intent/risk/authority; update the
actual spec/ADR/plan and dependent tasks where needed; repair an engine/environment gap through its
supported owner; retry scoped analysis/preparation and fresh preflight. Keep unrelated ready work
available, task IDs/baseline/history intact, and this analysis strictly read-only.

The accepted constitution's risk-selected sequence overrides upstream universal test-before-code
examples. Require relevant tests, meaningful red when test-first is chosen, and maintained scaffold
checks before dependent behavior; do not report coherent scaffold-first generation as a violation.
Confirm `Story delivery map` sizing/outcome/walkthrough and operation ownership. Required human
review belongs to each complete runnable story, with earlier gates only when explicitly agreed.
Missing scoped review/progression/deferral policies remain findings; checked tasks never imply acceptance.

For a selected native Foundation, check the plan against the sole typed
`eng/foundation-composition.json` and its Accepted owner/placement references. Report duplicate
legacy authority inputs, unresolved resource bindings, missing adapter capability and a source
Composition project whose only purpose is dependency collection or startup. Generated realm and
Compose files are outputs. Preparation and prepared startup belong to the maintained machinery;
product authorization, ownership, transactions/idempotency and journey tests remain implementation
work. Inspect existing readiness evidence read-only; analysis must never prepare or start services.
During adoption, reconcile only affected plans/tasks/retired placements, preserve valid work and
task identities, and require fresh implementation entry without repeating intake/bootstrap.
