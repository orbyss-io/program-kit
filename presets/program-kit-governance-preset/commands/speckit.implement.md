## Program Kit implementation guidance

Keep the native implementation flow, including its checklist decision, configured hooks, task order
and progress updates. Reuse current spec/plan/tasks and relevant architectural decisions. Preserve
completed tasks, IDs, existing code, unresolved failures and the user's local choices on resume.

Implement a coherent vertical outcome with its actual enabling dependencies. Resolve consequential
missing ownership, contract, policy or risk decisions before dependent edits; investigate routine
facts locally. Keep unrelated ready work available. No general toolkit receipt, confirmed-intake
hash, roadmap state, coding-unit qualification or hidden delivery checkpoint is a prerequisite.

Run the checks the selected action needs: compiler/analyzers and focused tests at the first coherent
increment, affected regressions for changed shared contracts, and complete applicable acceptance at
feature closure. Choose verification sequence by risk and the constitution. Existing engineering
wrappers are optional conveniences; documented direct project commands remain valid. Reuse passing
checks only while their relevant inputs/environment are unchanged; retain failures honestly.

Start a runtime, provider, browser or database only for an action/test that needs it. A generic
before-coding hook must not start the entire application. Missing device software needs a suitable
human-executed preparation command; project dependencies use the normal declared restore route.
Selected compiler, SDK, package and API contracts remain real constraints.

At the review points agreed in the constitution or plan/tasks, present exercised behavior, entry
point, prepared data/account, walkthrough, expected result, limitations and simulated externals.
Pause dependent product work until actual acceptance or an explicit scoped deferral. Repair and
diagnosis of the presented result remain available. Record the human's disposition in ordinary
notes; silence, elapsed time and a passing test cannot supply acceptance. Required deferred reviews
remain due before feature acceptance. Reopen affected decisions when substantive meaning changes.

Report completed and remaining work, actual commands/results and any reused evidence. Distinguish
engineering results, semantic review and human acceptance. A progress save or resume is not a full
acceptance boundary and does not require another broad matrix.
