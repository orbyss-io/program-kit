## Program Kit implementation guidance

Keep the native implementation flow, including its checklist decision, configured hooks, task order
and progress updates. Reuse current spec/plan/tasks and relevant architectural decisions. Preserve
completed tasks, IDs, existing code, unresolved failures and the user's local choices on resume.

Implement a coherent vertical outcome with its actual enabling dependencies. Resolve consequential
missing ownership, contract, policy or risk decisions before dependent edits; investigate routine
facts locally. Keep unrelated ready work available. No general toolkit receipt, confirmed-intake
hash, roadmap state, coding-unit qualification or hidden delivery checkpoint is a prerequisite.

For the current task or coherent increment, apply this coding method directly:

1. Read its intended behavior, owning responsibility, selected plan/research/ADR decisions and the
   relevant existing source. Trace important commitments to their reasons and source facts.
2. Read focused applicable pattern, integration and security guidance and verify exact selected
   dependency/API facts in the project's manifests, locks and authoritative documentation. The phase
   reference index is lexical discovery; correct missed or irrelevant context through review rather
   than loading the entire catalog or treating reference selection as a design verdict.
3. Identify semantic commitments to preserve and the local adaptation. Prefer actual framework
   mechanisms and supported extensions before adding wrappers, runners, parsers, projects or
   lifecycle owners. Adapt private file/class arrangement without reopening accepted meaning.
4. Implement the smallest coherent case. If code exposes a missing fact or invalid assumption,
   investigate it with targeted research or an appropriate experiment. Agent-written tasks do not
   authorize an unjustified design.
   Name that case's observable result and use existing local APIs/examples before expanding it.
   Compile/check its first small integration before replicating registration, settings or storage
   code. For a large safety-sensitive provider, establish one authorized binding, generated staging
   and exact-hash/no-overwrite publication case, then extend contention, expiry, drain and restart
   checks. The first case is engineering progress, not permission to accept an incomplete provider.
5. Run focused compiler/analyzer, architecture, security and behavior checks as applicable. Review
   actual source against the chosen semantics before replicating a new or uncertain approach.
   Apply the [first-operation source review](.specify/extensions/program-kit-governance/references/programming-guardrails.md#typed-boundaries-and-design-evidence):
   inspect actual method abstraction, owned state transitions, pure policy/provider split, effective
   configuration and required snapshots, deadline/resource ownership and operation-local placement.
   Trace one relevant adverse case. A green build, folder move or generic compliance claim cannot
   close these semantic questions. Preserve runtime/wire identities and native source inventories.
6. Route consequential deviations through the shared
   [engineering feedback method](.specify/extensions/program-kit-governance/references/engineering-feedback.md),
   correct the owning documents and affected tasks, then rerun affected review/checks. Preserve
   unrelated completed work and agreed human pauses; continue independent ready work.

Patterns may be adapted while preserving their explicit commitments. Exact templates apply when a
selected generator requires them; neither catalog qualification nor a per-task full-app acceptance
run is required for ordinary coding. A material product or architecture change needs its actual
decision owner; silently rewriting the plan cannot justify it.

Run the checks the selected action needs: compiler/analyzers and focused tests at the first coherent
increment, affected regressions for changed shared contracts, and complete applicable acceptance at
feature closure. Choose verification sequence by risk and the constitution. Existing engineering
wrappers are optional conveniences; documented direct project commands remain valid. Reuse passing
checks only while their relevant inputs/environment are unchanged; retain failures honestly.
The risk-based sequence above governs generic test-first ordering: an expected behavioral red test
is followed by its implementation, not treated as a blocker requiring another user prompt. Compiler,
tooling and unrelated setup failures do not establish that red test. Investigate unexpected failures
and stop dependent effects when necessary, while continuing independent ready work.

On resume, read the concise current status and follow links to relevant history. Reconcile stale
operative tasks and missing dependencies through the owning documents without erasing completed
work. Implement settings needed by the current consumer now; finish the complete inventory at
closure. Avoid repeatedly rereading unchanged catalogs or requalifying unchanged supplier behavior.

Start a runtime, provider, browser or database only for an action/test that needs it. A generic
before-coding hook must not start the entire application. Missing device software needs a suitable
human-executed preparation command; project dependencies use the normal declared restore route.
Selected compiler, SDK, package and API contracts remain real constraints.

At the review points agreed in the constitution or plan/tasks, present exercised behavior, entry
point, prepared data/account, walkthrough, expected result, limitations and simulated externals.
Pause dependent product work until actual acceptance or an explicit scoped deferral. Repair and
diagnosis of the presented result remain available. Record the human's disposition in ordinary
notes; silence, elapsed time and a passing test cannot supply acceptance. Required deferred reviews
remain due before feature acceptance. Reopen affected decisions when substantive meaning changes.

Report completed and remaining work, actual commands/results and any reused evidence. Distinguish
engineering results, semantic review and human acceptance. A progress save or resume is not a full
acceptance boundary and does not require another broad matrix.
Continue authorized ready increments until an agreed human review, genuine unresolved blocker or
completion. Finishing an internal task or saving progress alone is not a new pause boundary.
