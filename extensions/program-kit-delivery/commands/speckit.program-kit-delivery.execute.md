Read `.specify/extensions/program-kit-delivery/references/azure-execution.md`, the common delivery
reference and current consumer governance instructions. Preserve the accepted business and Git
technical authorities. This command guides ordinary sessions and deterministic tools; it never
launches coding agents, pipelines or background workers automatically.

Resolve the pinned active profile and registered repository locations. An older enabled profile
without execution policy needs an explicitly reviewed profile migration using the reconciliation
command. Do not upgrade authority implicitly or replace the checked-in binding/history. Repository
locations are lookup inputs, not authority overrides. Never put credentials in configuration.

Include native board mapping in execution onboarding. Start from `azure-board-default.json`, resolve
the actual team/board identities and validate per-type workflow states and column mappings with
`board-plan`. Present the mapping and obtain business and technical `board-approve` decisions, then
`board-apply`. The approved board policy binds the current delivery profile; it adds operational
presentation mappings without rewriting existing execution plans or pipeline evidence. Existing
spaces require this explicit approval before claiming board synchronization is enabled.

Execution start, scope-plan application, claim activity changes and evidence-backed completion
queue native state/tag changes in the same coordinator commit as the governed decision. They then
publish conditionally. A synchronization error leaves a durable pending operation and blocks further
affected progression: use `board-resume --operation-id ...`; never repeat an uncertain native PATCH.
Use `board-sync --work ...` to bring previously verified work into the approved native mapping.
Reconcile intervening human changes first. `board-abandon` needs a newer accepted native revision
that fences the previous update. Parent closure uses an explicit `parent-outcome-plan` and
`parent-outcome-accept`; child completion alone cannot close a Feature or Epic.

Use `ready` to distinguish refinement from implementation readiness. Explain business priority,
assignment, current claims, dependency conditions, milestone risk and coordination findings. Respect
explicit executor/team eligibility. Broad path overlap is advisory; confirmed incompatible resources
need an attributable scope/contract decision or sequencing. Unknown scope is not independence.

Prepare an execution `plan` linking real committed technical artifacts, bounded planned paths,
contracts/resources, named acceptance checks, activity-specific dependencies and optional dates.
Present the concrete scope, executor, verification and scheduling consequences. Obtain business and
technical approval of the same digest using `approve`, then `apply`. Scope changes require a new
review, not an edit to an approved proposal. An existing claim must be explicitly withdrawn or handed
off before its planning basis can be replaced. Preserve superseded evidence.

Use a distinct session identity to `claim` the selected work. The provider claim is authoritative;
the local execution receipt merely identifies it. Keep different concurrent sessions in separate
checkouts so their receipts and working files do not collide. `checkpoint` before implementation,
integration, review/publication and substantial phases. Actual start is recorded when implementation
begins, not at assignment/claim. Check source expansion and generated-source dependencies. Observe
pause/review states, explicit takeover generations and the bounded outage policy. Never declare a
lost session current because its old local receipt still exists.

Publish the supported native tags/links and platform-hosted readable view with `publish-view`.
After an ambiguous write, resume the exact projection ID; never blindly repeat a native mutation.
Human text, comments and unrelated tags remain intact. Reconcile human changes before proceeding.
Native closure does not release a claim, supply evidence or grant business acceptance.

Use `evidence-plan` and `evidence-record` to verify exact provider runs/artifact bytes or explicitly
allowed manual observations. A successful test job is distinct from an authorized verifier decision.
Use `progress-plan` and `complete` for integrated implementation, verified delivery and business
acceptance in order. Present exact evidence and obtain the appropriate human decision. Release
implementation claims only when the integrated activity is complete; outstanding test/acceptance
obligations remain open. Never manufacture completion from child counts, native status or PR badges.
