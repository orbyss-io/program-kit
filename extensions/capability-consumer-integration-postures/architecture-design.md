# Capability consumer integration postures

Canonical source: `architecture-design.json`
(`sha256:666cf457a32702cd8ecf29fbdf412a99bd7187e953c5e1696d82bd4d6fa9d1b0`),
governed by Architecture Design `2.0.0`.

This document is a reviewer projection. If it differs from the canonical JSON,
the JSON governs.

## Outcome

Program Kit offers reviewed, project-scoped AI-provider adapters without
deciding how a consumer repository uses them. Each consumer product documents
one of three postures:

1. `none`: no Program Kit provider integration is exposed;
2. `local-optional`: contributors may initialize a supported provider locally,
   and keep the generated binding and ownership evidence outside version
   control;
3. `repository-managed`: the product owner commits selected provider bindings
   and ownership evidence so a fresh clone can discover them.

The product README must state the selected posture and link to the exact pinned
Program Kit capability-initialization documentation. A bare link cannot explain
whether absent integration is intentional.

## Ownership boundaries

The consumer owns its posture, README, ignore rules, and tracking choices.
Program Kit never selects a posture, edits `.gitignore`, stages or commits
files, installs a provider globally, grants trust or permissions, or starts
development work.

Program Kit owns only:

- the finite reviewed provider contract registry;
- exact thin-wrapper rendering;
- project-contained initialization and removal mechanics;
- exact ownership evidence and migration rules;
- provider-neutral posture and onboarding guidance.

Capability definitions remain canonical in the verified bundle. Provider
wrappers point to those definitions and do not copy procedures or grant
authority. Runtime libraries and generated applications do not load capability
prose, provider configuration, ownership locks, or posture state.

## Reviewed providers

The initial finite adapter set is:

| Provider | Reviewed project-skill root |
| --- | --- |
| Codex | `.agents/skills/<capability-id>/SKILL.md` |
| Claude Code | `.claude/skills/<capability-id>/SKILL.md` |

A provider is supported only when its identifier, discovery root, template,
manifest, compatibility boundary, documentation, and tests are reviewed
together. Folder-name recognition is not an adapter contract.

The provider evidence is recorded in `provider-contract-evidence.json`.
Implementation must recheck that evidence and stop the affected work unit if an
official contract has materially changed.

## Multi-provider ownership

One versioned workspace lock records the complete finite set of Program
Kit-owned provider bindings. Initializing one provider adds or updates that
provider while preserving every other exact owned provider.

Each recorded output binds enough evidence to verify the exact generated bytes.
Unsupported providers, path escapes, duplicate normalized paths, unowned
collisions, incomplete bundles, or ambiguous legacy state fail before mutation.
Writes are deterministic and transactional: interruption cannot leave a
partially updated binding or ownership lock.

Removal is an explicit human-started command. It removes only one selected
provider whose current wrapper bytes still match Program Kit's exact ownership
evidence. Modified or unowned files stop removal. Removing the final provider
removes the empty lock; it does not infer or write a consumer posture.

## Legacy migration

Legacy single-provider locks remain readable only for exact migration during an
explicit initialization or removal command.

For Codex, exact Program Kit-owned wrappers at the legacy
`.codex/skills/<capability-id>/SKILL.md` location move to
`.agents/skills/<capability-id>/SKILL.md`. Modified, incomplete, conflicting, or
unowned legacy files stop the operation without partial mutation. Legacy paths
are not treated as current provider contracts.

The lock-shape and Codex-root changes require a new capability-bundle revision.
The Domain Semantic Engine consumer keeps its current
`repository-managed` Codex posture and is migrated only after the new bundle
and migration mechanics are verified.

## Components

- `pkid:component:program-kit:capability-provider-contract-registry` owns the
  finite allow-list and exact adapter contracts.
- `pkid:component:program-kit:capability-workspace-initializer` verifies a
  bundle and transactionally adds or updates one provider.
- `pkid:component:program-kit:capability-workspace-remover` verifies exact
  ownership and transactionally removes one provider.
- `pkid:component:program-kit:capability-consumer-guidance` explains posture,
  setup, removal, provider support, and selective Git tracking.

No component is runtime-activatable.

## Static conformance

The selected disposition is `reuse-existing`, bound to
`static-conformance-disposition.json`
(`sha256:aa422e16ebbfc5fb038a29adbfd5d9072122292543f82b07ca9e8c87cbb340af`).

The existing private Program Kit C# source-quality gate applies only to
Program Kit-owned implementation. No new gate, analyzer extension, or consumer
attachment is proposed. Provider discovery, filesystem ownership, Git posture,
migration, removal, and clean-session behavior require executable tests and
human review.

## Acceptance shape

Acceptance covers:

- fresh initialization for Codex and Claude Code;
- coexistence and idempotent reinitialization;
- exact legacy lock and Codex-path migration;
- exact provider removal and final-lock cleanup;
- refusal on tamper, collision, path escape, unsupported provider, incomplete
  bundle, cancellation, and transaction recovery;
- absence of provider-global, `.gitignore`, Git-index, runtime, and unrelated
  file mutation;
- exact bundle, capability, adapter, and lock digests;
- clear clean-clone and local-optional onboarding guidance.

This review artifact implements none of those behaviors. Implementation
requires explicit human approval of the exact canonical design and plan
digests.
