# Feature intake

Read the current request, existing spec, product intent, constitution, relevant ADRs and architecture.
Use the shipped grilling skill proportionally. Reuse settled language, journeys, roles, policies,
lifecycles, quality constraints and supplied examples. Ask only consequential unresolved questions.
A rough request and a detailed existing design are both valid inputs.

Select one useful actor outcome with coherent success and material failure examples, scope,
non-goals, assumptions and dependencies. Challenge oversized feature boundaries and fragments
without an independently reviewable outcome. Preserve relevant future questions with owner and
trigger in the normal spec/plan. Do not mechanically import every global question into this feature.

Explain choices, disclosed defaults and alternatives; obtain the human's actual confirmation of
the selected product meaning. Record that decision and any limits in the spec or a readable intake
note. A missing review/status/hash/roadmap ID is not itself a blocker. Substantive changed meaning
needs affected human review; formatting, toolkit versions and unrelated features do not reconfirm it.

Use ordinary native speckit.specify and speckit.clarify. Include actor journeys, acceptance examples
and requested automated behavioral tests; leave technologies and test frameworks for planning.
The consumer may choose another stack or approach. Consult relevant knowledge, research unknown
contracts and disclose unsupported automation. Program Kit qualification is not consumer consent.

The optional specification_intake.py helper can begin/context/review/check a structured brief when
useful. It enforces only its own supplied input. check-spec inspects a normal titled specification;
no confirmation.json, review-basis.json, SHA256, roadmap entry or exact intake-reference ceremony
is required. Optional links/scopes must point to real repository-contained input when supplied.
An optional brief does not establish human acceptance merely by existing or passing inspection.

Preserve the agreed human review points in ordinary native plan/tasks/checklist notes. Each story
needs useful independent walkthroughs and an actual human acceptance decision before progressing
where the user agreed to pause. Implementation guidance belongs to native phases and focused
engineering helpers; intake supplies no runtime, provider, implementation or release evidence.
