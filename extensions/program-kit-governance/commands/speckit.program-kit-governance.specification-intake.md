When `.program-kit/consumer-upgrade.json` exists, inspect compatibility before creating
a feature directory. Use `specification_intake.py --repository . compatibility --request-file
<existing-brief-or-temporary-request.json>` with known architectureScope, contracts and
affectedPaths. Refine missing ownership honestly and resolve only due affected work.
Preserve unchanged confirmed product intent; toolkit version changes do not reconfirm it.

Use the normal feature request and any existing specification/intake. Follow the installed grilling
method at `.specify/extensions/program-kit-governance/commands/speckit.program-kit-governance.grilling.md` proportionally: investigate facts, ask only unresolved product/architectural questions,
and preserve settled answers and accepted defaults. The user owns the roadmap; a missing or
non-Ready roadmap entry is not an intake blocker. Never require renewed bootstrap/ratification.
Use references/functional-discovery.md to read the relevant established concepts, lifecycles,
policies/conditions, journeys and experience choices from the existing project intent/design.
Reuse settled answers; deepen the selected outcome and its material alternatives with the human.
Carry the stable product and journey references into the brief/specification; do not restart a
whole-product interview or choose a generic UI layout in place of the agreed experience.
One roadmap epic can have several feature specifications. Select the candidate's stable feature ID
separately from its parent epic. Read its canonical `seed`, boundary rationale, detailed source
input, assumptions, open questions and known feature prerequisites. Reuse supplied answers rather
than reducing the seed to a fresh generic questionnaire. Challenge both oversized boundaries and
fragments that provide no useful reviewable outcome. An outline seed can remain incomplete until
this interview; a rich seed need not repeat discovery already settled.

For new feature intake use `specification_intake.py begin --entry <epic-ID> --feature <candidate-ID>
--request "<current request>"` as one physical command. Use the same `--feature` with context,
review, confirm and check. This creates a feature-owned draft, not a specification or branch. The
parent epic does not own the feature's confirmation. Preserve the existing legacy `--entry`-only
path for consumers whose confirmed brief predates independent feature identities.

Source commitment and commissioning are separate: a user may now select a previously exploratory
seed. Disclose that source classification in review, clarify the current scope and obtain the actual
feature confirmation; do not silently rewrite the source map's commitment or require roadmap-status
promotion as an intake gate. Present a material change to epic scope, priority or dependencies in
the same affected review. A shared architecture change retains scoped architecture review.
For sign-in/recovery styling, identify the relevant application and identity-provider screens.
Carry established brand/accessibility intent across those owners; planning maps Keycloak-owned
screens to login-theme customization. Do not invent a provider-styling exclusion because the
feature request omits that implementation name. Preserve explicit exclusions or assigned deferrals.

Reuse established application/API boundaries, logical databases and their owners, shared identity
authorities, clients, audiences and application/delegated call intent. Ask only for unresolved
product relationships; a database server is distinct from a logical database and an external
identity authority requires no owned server. Carry these stable identities into architecture's
typed composition input. Provider import fields and generated Compose syntax belong to adapters,
not an additional intake questionnaire or a new C# Composition project.

Clarify actors, user-visible outcomes, story priority, independent acceptance examples and relevant
failure cases. Quantify material quality constraints and identify assumptions/dependencies. Ask only
questions that affect this feature; do not force every risk category into every intake. Carry the
answers and the constitution's testing policy into the normal spec, including an explicit request
for automated behavioral tests. Leave implementation technologies and test frameworks for planning.

Use specification_intake.py begin/review/confirm/check when maintaining a structured intake.
Its `context` output exposes the existing product `open_items` as `productFrontier`. During this
feature's review, explicitly decide each item's applicability in the existing brief `decisions`:
link `productOpenItem` to its exact source ID and `productOpenItemSha256` to the supplied item hash.
Answer or adopt a supported default, carry an applicable unresolved decision with its actual
`owner`, `trigger` and structured `duePhase`, or use `excluded` with a concrete explanation that
it is unrelated to this feature. Do not infer applicability or due phase from English trigger text.
This adds no prerequisite ledger. Normal phase checks reject a selected deferred product decision
when its explicit phase is due; settle and review the affected feature answer before continuing.
Product answers cannot replace executed compatibility, runtime or provider evidence. Later unrelated
frontier additions do not reopen a confirmed feature; changes to its linked source conditions do.
Reuse an unchanged confirmed brief. Toolkit versions, document formatting, test results and
other features do not require another confirmation. Material changes to the brief's product
choices need the user's actual answer; never fabricate it. Reference the brief in the spec.
New specifications record both `Specification roadmap entry` (the epic) and `Specification feature
ID`, plus the exact confirmed brief path and hash. Several specs under one epic have independent
briefs and confirmations. Source seed capture alone never confirms unseen feature behavior.
Normal Spec Kit clarification handles ambiguity introduced during drafting. Do not create
parallel approval/recovery dossiers or invent bootstrap obligations for feature work.

Carry small coherent runnable actor journeys, explicit non-goals, independent walkthroughs and
connected success/material failure outcomes into fresh specification. Estimate preparation,
integration and verification to human review; split oversized stories by useful journeys before
tasks, or disclose larger-story effort/rationale. Human acceptance is per story, not each operation.
Use balanced verification under the ratified constitution: known scaffold-first generation followed
by maintained checks/missing consumer tests; critical/uncertain behavior prefers meaningful test-first.
Adoption of this workflow abandons affected partial features and reruns all phases from fresh spec.
Unchanged confirmed intake informs that fresh spec without repeating the whole product interview.
