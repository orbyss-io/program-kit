Read `.specify/extensions/program-kit-governance/references/consumer-upgrade.md` for
the maintained preparation, migration planning and destination activation method.
Use `.specify/extensions/program-kit-governance/references/consumer-migration-recipes.json`
for versioned reusable recipes. This is an explicit conversational entry, never an
automatic update, bootstrap restart, coding-worker dispatch or external rollout.

Follow `references/device-toolchain-policy.md` whenever device software is missing/mismatched.
Pause dependent work, present the authoritative version, detected path/version and official
user-terminal commands, and wait for completion. Verify actual paths/versions in a fresh session;
never run SDK/Node/npm/Python/Spec Kit installers or mask the mismatch with local tools or PATH.

Select the exact verified target release and a committed consumer baseline. Stage the
release outside the consumer and prepare a fresh isolated worktree with the release's
`scripts/consumer_upgrade_workspace.py prepare`. Inventory source installation, owned
ignored setup, customization and authority. Resolve real missing setup proportionally;
do not manufacture installation history or blindly copy caches. The adapter scopes
SPECIFY_INIT_DIR to each intended child and preserves source setup. Re-establish local
runtime/readiness through maintained commands. Preserve failed preparation evidence.

In isolation run `{SCRIPT} assess --guidance <release-guidance>` and inspect actual
architecture, contracts, dependency selections, current code and unfinished features
across the whole consumer. Use cumulative semantic changes and target supersession,
including customization. Describe incomplete history honestly. A default offers adoption;
supported retained decisions and unchanged intent/confirmation carry forward.
Ask grouped consequential questions, offer only valid alternatives and resolve real
unsupported retention. Mechanical setup and context regeneration need no new approval.
Use existing architecture/constitution review and dependency_profiles.py draft/accept
for their substantive choices. Never fabricate reviewer/approval provenance.

Always offer an optional software update review during this upgrade, even when the
consumer already uses the release's default dependency profile. Group the choice:
keep current versions, review qualified dependency profiles, or review all repository
software. Honor an already stated choice and continue installation when the consumer
declines or defers this review. Use the software review method in consumer-upgrade.md.
An upgrade request alone does not select newer dependency versions.

Record decisions and concise planned/conditional/deferred migrations in the single
coordination record via decide/brief. Group shared contracts once across owners and
dependency closure. Record evidence, outcome/invariants, trigger/due phase, dependencies,
method, uncertainties and next action. Do not eagerly generate every detailed plan.
Investigate enough to establish compatibility and due phases; do not hide a shared
upgrade incompatibility as deferred work. Complete upgrade-due migrations before success.

Use `{SCRIPT} reconcile` to identify affected architecture/spec/plan/tasks. Edit only
affected existing areas, preserve requirements, checked tasks and IDs, and resume from
the earliest affected phase. A feature at tasks does not automatically return to specify.
Use normal task_draft resume, analyze and preflight; preserve founding bootstrap history.
Use the release-owned workspace install adapter for the sequential updater.
Run relevant baseline and current actual application checks; distinguish unrelated
baseline failures, introduced failures and inability to verify affected behavior.
An installer/graph/plan PASS cannot establish consumer correctness or human acceptance.

At migration pickup inspect current code/dependencies and recipe, resolve uncertainties,
then create/link ordinary detailed plan/tasks/tests. Reopen changed dependent inputs,
implement, execute verification and record actual invariant/semantic results. Use a bounded
consumer-specific reviewed proposal when no recipe fits. Scans before specify and during
planning match owners/contracts/planned migrations and carry dependencies in normal docs.
On discovery immediately append a classified local recovery brief; preserve prior findings,
keep unaffected work available and turn demonstrated omissions into regressions.

Before reviewed merge, reassess intervening development and installation changes using
the combined isolated candidate and current checks. Merge under consumer authority.
Then use the workspace adapter activate to reconcile ignored destination assets and verify
required destination readiness with recovery retained. Git merge alone is not activation.
Failed/interrupted activation preserves evidence and restores original setup; conflicting
edits require scoped recovery without overwrite. External rollout/data recovery stays
separately planned and authorized.

Use `{SCRIPT} status` for honest scoped next actions. An upgrade may finish with credible
deferred migrations after consequential choices and upgrade-due work are resolved.
Use `{SCRIPT} export --output <fresh-local-report.json>` for minimal sanitized maintenance
evidence with provenance and recovery outcome. Review for sensitive consumer facts;
original logs/architecture/source remain local unchanged. Never send automatically.
