---
description: Repair an accepted bootstrap after technical readiness failure while preserving its run and approvals.
---

Read the handoff supplied in `$ARGUMENTS` and this extension's
`references/bootstrap-lifecycle.md`. This is maintenance of an accepted baseline, not new intake
or a new bootstrap workflow. The originating run remains immutable historical evidence.

Invoke the bootstrap-closure instructions against the existing first slice. Own every filename,
ID, manifest, target and placement decision. Preserve immutable intake/assessment, Accepted ADRs
and ratified constitution. Use scoped follow-on decisions for changed design authority. Do not
remove a retained condition or change NOT READY to READY to make validation pass.

Follow the exact handoff commands to generate the recovery review packet. It exposes before/after
hashes, source dispositions, compatibility evidence and acceptance scope. Present that concrete
packet for the user's final architecture review; the previous bootstrap approval does not authorize
new architecture decisions. The user-owned `accept --verdict approve` command records renewed
review. Do not run that approval command on the user's behalf without explicit approval of this packet.

After approval, invoke the readiness producer with the same handoff and current evidence. Run its
named terminal batch, then the handoff's completion command only when eligible is true. A valid
non-ready result preserves evidence and reports bounded corrective work. A malformed report is a
producer defect. Missing/stale authority is a governance correction. None means the user rejected
the previously approved architecture. Report recovery complete only after `validate-completion`
passes and the linked recovery completion record exists.
